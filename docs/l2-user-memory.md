# 用户长期记忆：管理页面、正式版本与候选隔离

L2 保存可跨应用复用的用户偏好。类别固定为语言偏好、视觉风格、技术栈倾向、体验偏好，具体内容是自由文本。同一类别可以保存多个独立属性，没有每类三条限制，也不自动清理历史。用户可以通过聊天表达偏好，也可以从右上角头像菜单进入“长期记忆”页面（`/user/memory`）直接管理。

## 管理页面与接口

页面分为“已生效”和“待确认”，分别提供分页、类别筛选和关键词搜索；“变更历史”在侧边抽屉展示操作来源及修改前后内容。管理列表显示保存的完整记录，不受 512 Token 的聊天召回预算限制。

新增时可以选择“立即生效”或“先存为待确认”。直接生效前先检查同属性的已有正式值，有冲突时展示替换内容。已生效记录可以编辑或撤销；候选可以采用或取消。页面手动保存的候选设置 `requiresConfirmation=1`，后续弱证据不会让它自动晋升，须明确确认。

下列接口均为 POST，完整路径带服务端上下文前缀 `/api`。用户身份从登录会话取得，不接受客户端指定 `userId`：

| 接口 | 请求要点 | 返回内容 |
| --- | --- | --- |
| `/user/memory/list` | status 为 ACTIVE 或 CANDIDATE；可选 category、keyword；pageNum 从 1 开始，pageSize 为 1～50 | 当前页记录、筛选后的总数、正式与候选总数 |
| `/user/memory/preview` | category、attributeName | 归一化后的属性名及当前正式版本，无写入 |
| `/user/memory/change` | requestId、action 及对应操作参数 | changed、目标 ID 与所在区域 |
| `/user/memory/history` | pageNum、pageSize | 操作来源、时间和变更前后内容，按时间与 ID 倒序 |

手动操作协议与模型抽取协议分别定义：

| action | 参数与行为 |
| --- | --- |
| CREATE | category、attributeName、content、saveMode；立即生效时携带预览得到的 expectedActive |
| EDIT | target、content；类别和属性沿用目标，内容改变时创建正式新版本 |
| ADOPT | 候选 target、页面看到的 expectedActive；在事务中采用并处理正式替换 |
| REVOKE | 正式 target；撤销后停止召回，历史保留 |
| CANCEL | 候选 target；不改动正式记忆 |

`target` 和 `expectedActive` 均使用 `{"id":"…","revision":"…"}`，ID 与版本必须按字符串传输。`expectedActive=null` 表示页面当时没有同属性正式记录；保存前后状态不一致时返回业务码 `40900`，前端刷新列表并要求重新确认。重复确认、数值型 ID、越权目标、非法类别和超长内容均由后端拒绝。

每次操作生成一个 UUID `requestId`；网络超时后的相同操作重试沿用它。后端保存规范参数摘要和原返回值：同请求同参数复用原结果，同请求不同参数拒绝。查询可取消，标签切换或账号变化后迟到的旧响应不会覆盖新页面；登录失效会清空内容并返回带原页面地址的登录页。

## 属性、版本与候选

`memoryKey` 表示偏好对象，`content` 表示偏好取值。例如 `ui.default_language` 是页面默认语言，`code.comment_language` 是代码注释语言。页面中文与注释日语可以同时生效；同一个页面默认语言只能有一个生效版本。

新增操作提供不含取值的 `attribute`，后端将常见属性名称和别名归一化。未知属性使用“类别＋规范化属性名称”的摘要分配扩展键，不使用内容取值生成键。模型应优先复用已有属性名。任意自然语言同义关系不能只靠数据库唯一索引证明；仍依赖模型识别和评测。

| 数据表 | 保存内容 | 状态 |
| --- | --- | --- |
| `app_memory` | 正式记忆及历史版本 | `ACTIVE`、`SUPERSEDED`、`REVOKED` |
| `app_memory_candidate` | 独立候选、已采用和已取消的候选 | `CANDIDATE`、`PROMOTED`、`REVOKED` |
| `app_memory_evidence` | 指向具体区域、具体记录的去重证据 | FORMAL / CANDIDATE 区域；CHAT / MANUAL 来源；EXPLICIT / IMPLICIT 证据 |
| `app_memory_event` | 变更历史、手动请求去重与原返回结果 | CHAT / MANUAL 来源；无实际变更的去重记录不显示在历史中 |

前两张是业务表，其余是辅助证据和操作记录。候选不参与生成模型召回；候选的普通新增、强化和撤销不改变正式内容、证据、排序时间或缓存。

明确确定的全局要求可以直接生效。隐含倾向先进入候选，至少两个不同完整用户回合的有效证据、没有生效冲突、没有撤销限制时才允许自动晋升。若多个互斥候选都达到次数，也等待明确选择。正式偏好存在时，弱冲突即使积累更多次数也只能留在候选区。用户要求“先记候选、等确认”按未确认处理。

确认候选会在事务内新建正式行，候选改为 `PROMOTED`，双向记录 `originCandidateId` / `promotedMemoryId`。正式值改变时新增版本，通过 `supersededBy` 关联旧版本。例如下列 ID 仅用于说明：

| ID | memoryKey | content | status | supersededBy |
| --- | --- | --- | --- | --- |
| 101 | ui.default_language | 中文 | SUPERSEDED | 102 |
| 102 | ui.default_language | 日语 | SUPERSEDED | 103 |
| 103 | ui.default_language | 中文 | ACTIVE | NULL |

第三条中文是新行；第一条不复活。`revision` 是每行的并发校验计数，补充证据也会增加它，不代表上述业务版本序号。

撤销保留记录并写入 `revokedByTurnId`。撤销正式属性后，旧候选或后续隐式证据不能自动重新激活它；新的明确要求可以建立新版本。撤销候选只撤销该候选，不撤销生效正式记录。明确重新确认时，新正式版本只采用撤销界限之后的证据。撤销不等于选择相反内容：“不要自动播放”是新增偏好，“忘记不要自动播放这条偏好”才是撤销。

## 聊天抽取与后端校验

现有稳定回合钩子按用户防抖，按应用记录抽取游标。只有完整回合的用户文本提供证据，助手回复只用于确定回合已完成；工具结果和生成代码不作为偏好证据。应用归属在准备阶段和提交阶段都由后端核验。

模型接收分区记忆、真实目标 ID、回合 ID 白名单和新增用户文本。当前正式、候选、必要撤销信息分页提供，同属性条目尽量放在同一窗口；所有窗口完成后才合并、校验并提交。分页矛盾、未知目标和过期快照整批失败，保留游标并退避重试，不把未展示的记录当成不存在。

协议示例：

```json
{
  "operations": [
    {
      "action": "REPLACE",
      "targetId": "102",
      "category": "语言偏好",
      "content": "新应用页面默认使用中文",
      "scope": "USER",
      "evidenceType": "EXPLICIT",
      "turnIds": ["9101"]
    }
  ]
}
```

| 操作 | 必需业务字段 | 后端行为 |
| --- | --- | --- |
| ADD | category、attribute、content | 归一化属性，检查重复、撤销和冲突；弱冲突可新增独立候选，明确冲突须引用已有目标 |
| REPLACE | targetId、category、content | 按目标继承属性；明确要求新建正式版本，弱倾向只写候选 |
| REINFORCE | targetId | 为对应记录补充去重证据；明确确认候选可触发晋升和正式替换 |
| RETRACT | targetId，且 evidenceType 为 EXPLICIT | 仅撤销指定目标；同一撤销重试保持幂等 |

候选正文保存具体的待确认取值，置信程度由状态和证据类型表达。用户明确采用已有候选时，必须用 `REINFORCE` 引用该候选 ID，并使用 `EXPLICIT`；后端据此创建正式版本并结束该候选，不能通过改写正文另建同义正式条目来代替采用关联。

所有操作都需要 `scope`、`evidenceType`、非空 `turnIds`。只有 `USER` 持久化为 L2，`APP` 和 `THREAD` 不写全局偏好。针对目标的操作可回显类别或属性名，但必须与目标一致；强化和撤销不接受 `content`。ID 必须是正 Long 范围内的十进制字符串，不接受浮点数、溢出、负数或伪造回合。

后端拥有用户 ID、新记录 ID、时间戳、最终状态和 SQL 的决定权。模型不能指定表名、状态或 SQL。解析、状态规划、仓储写入分别由 `UserMemoryOperationParser`、`UserMemoryChangePlanner`、`VersionedUserMemoryRepository` 负责。

## 事务、证据与缓存

模型调用发生在数据库事务之外。提交时锁用户行，使用当前读重查正式、候选和游标，校验模型快照及目标版本；先生成完整变更计划，校验通过后再执行 SQL。替换先释放旧生效槽，再插入新正式行。聊天抽取的正式/候选变更、证据、操作历史和成功游标在同一事务提交，任何一步失败都会回滚。

手动管理与聊天抽取共用 `UserMemoryChangePlanner` 和 `UserMemoryConsistencyCoordinator`。手动操作不调用模型，不伪造聊天消息，也不推进聊天抽取游标；操作记录、记忆版本、证据和请求去重结果在同一事务提交。操作 ID 在新记忆 ID 之前分配，并与真实聊天回合使用同一有序 ID 空间，防止旧聊天结果倒退页面刚确认的值。

数据库生成列和唯一索引保证每用户每属性最多一个 `ACTIVE`，并避免重复待确认内容。证据按 `(userId,targetKind,targetId,turnId)` 去重。`turnId`、`lastEvidenceTurnId` 和 `revokedByTurnId` 保留原列名；CHAT 来源指向真实用户回合，MANUAL 来源指向 `app_memory_event` 中的操作 ID，不把手动操作冒充聊天回合。同一证据重复处理不会增加计数；跨应用后处理的较小回合 ID 仍可提供新的同内容证据，但较旧的冲突改口不能倒退已确认偏好。

迁移数据使用 `legacyEvidenceCount` 保存原计数，`legacyEvidenceTurnId` 保存已知最后回合。没有保存过的旧证据明细不补造；新计数为旧基线加新账本的有效证据数。

管理功能启用前的记录在历史中显示为“此前保存的”快照；新操作显示为“手动操作”或“聊天中更新”。不会为旧数据编造过去的修改时间或操作过程。

正式召回缓存为 `mem:pref:v3:{userId}`。纯候选变化不访问正式缓存。正式变化在写入前严格失效新版缓存，提交后清理新版及旧 v2/legacy 键；Redis 失效失败会让正式变更进入重试。缓存回填与更新沿用用户级进程锁。数据库写入另有用户行锁、乐观版本和唯一约束，但整个应用仍按单后端实例设计，不能据此宣称全链路已支持多实例缓存协调。

## 召回

由应用归属确定用户，先读正式缓存，未命中时以每页 100 行查询 `app_memory` 的 `ACTIVE` 记录。排序为明确证据优先、更新时间降序、ID 降序。按 ID 去重后保留完整条目，例如：

```text
- 语言偏好:页面默认语言：新应用页面默认使用中文
- 语言偏好:代码注释语言：代码注释默认使用日语
```

实际注入片段（包含说明文字和确认消息）最多 512 Token。放不下的条目不截断，也不从数据库删除。缓存读取时同样检查当前预算，超限缓存自动失效并回源重建。这里是用户维度的结构化查询与预算筛选，没有使用向量检索。候选、历史、撤销不消耗正式召回预算。

删除来源应用时，正式、候选、证据和操作历史的 `appId` 都解除关联，保留全局内容、证据和历史；同时删除该应用的抽取游标并取消迟到任务。

## 迁移与验证

已有数据库先执行 [正式与候选分表迁移](../sql/migrations/2026-10-30-l2-user-memory-isolation.sql)，再执行 [管理页增量迁移](../sql/migrations/2026-10-30-l2-memory-management.sql)。后者添加候选确认标志、证据来源和操作历史表。新库使用 `sql/schema.sql` 或 `prod/sql/schema.sql`。操作边界及回退步骤见 [迁移说明](../sql/migrations/README.md)。迁移不会在应用启动时自动执行。

行为测试包括状态机、参数边界、分页、缓存、调度和删除回归。`UserMemoryMysqlIntegrationTest` 通过显式测试环境变量启用，在隔离 MySQL 服务中创建随机测试数据库并清理，验证真实 Mapper、版本链、唯一约束、回滚和并发。

`UserMemoryModelEvaluationTest` 单独启用，使用合成中文对话评估真实抽取模型的范围、目标和最终状态。固定 JSON 单测通过不能替代语义评测；当前样例通过也不等于任意自由文本都能无误消歧。本次执行日志、迁移核验结果和真实模型原始输出保存在项目 `.codex/reports/l2-memory/`。

本次另完成了真实 HTTP 端到端测试：17 项场景通过，覆盖 15 次成功生成、原有 30 秒防抖、MySQL/Redis 落地、实际模型输入、跨应用生成、撤销和用户隔离。报告保存在 `.codex/reports/l2-memory-e2e/端到端验收.md`。

管理页另有 364 项后端回归、309 项前端测试、26 项真实 HTTP 验收和 15 项浏览器检查；其中后端回归包含 15 项真实 MySQL 测试与 8 组模型评测。覆盖手动操作、证据来源、请求重试、版本冲突、并发修改、用户隔离、缓存失效、登录过期和中文版本链，前端类型检查与生产构建也已通过。记录位于 `.codex/reports/l2-memory-management/验收记录.md`。测试账号和测试偏好仅写入隔离数据库。
