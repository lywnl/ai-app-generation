# L1 摘要 Redis 缓存 — 消除 messages() 的 MySQL 放大读

## 1. 背景与问题(已核实)

分层记忆一期已交付 L0 热窗口 + L1 滚动摘要 + 冷启动重建。L1 摘要的**读取路径**存在一个被工具循环放大的 MySQL 重复读:

- `LayeredChatMemory.messages()`(`LayeredChatMemory.java:45-47`)每次拼装上下文都调用 `summaryService.getCurrentSummary(appId)`。
- `MemorySummaryServiceImpl.getCurrentSummary`(`:142-150`)执行 `summaryMapper.selectOneByQuery(...)`,即一次 MySQL 查询。
- vendored 的 `AiServiceStreamingResponseHandler`(`:120-169`)在工具循环里:每完成一轮工具调用(`aiMessage.hasToolExecutionRequests()` 为真),就用 `messagesToSend()`(`:165` → `getMemory().messages()`)重建 `ChatRequest` 并递归出新 handler。

**结论:`messages()` 每轮工具调用触发一次。** 一次 `VUE_PROJECT` 生成若有 N 轮工具调用,`messages()` 被调用 N+1 次,即 **N+1 次 MySQL 摘要读**。而摘要仅由对话结束后的异步钩子更新,**单轮对话内绝不改变** → 其中 N 次为完全重复的浪费读。`HTML`/`MULTI_FILE`(无工具)为每轮 1 次。

## 2. 目标与非目标

- **目标**:消除 L1 摘要读取在工具循环内的重复 MySQL 查询,降低 DB 压力与首字延迟。
- **非目标(YAGNI)**:不改触发条件(新增 ≥8 条 → token 阈值)、不校准中文 token 估算、不动 5 段摘要 prompt、不做 L2。这些是独立优化项,本次不碰,以保持改动可整体评审与回滚。

## 3. 方案决策

选 **A:Redis 共享缓存 + write-through**。

| 方案 | 结论 | 理由 |
|---|---|---|
| **A Redis 共享缓存** | ✅ 采用 | 多实例安全;与现有 Redis/Redisson 架构一致;改动集中单类 |
| B Caffeine 进程内 | ❌ | 最快但多实例间有"最长一个 TTL"的陈旧窗口(实例 A 更新摘要后实例 B 读旧值),与"长对话/跨会话不失忆"的初衷相悖。项目已有 Redisson 分布式限流 → 按多实例设计 |
| C Caffeine+Redis 两级 | ❌ | 过度设计;摘要只是每 app 一个小字符串,不值得两级 |

## 4. 可用基建(已核实,无需新增依赖)

- `RedisCacheManager`(`RedisCacheManagerConfig.java`)+ `RedisConnectionFactory` 已装配。
- Spring Boot 在该 `RedisConnectionFactory` 上**自动装配 `StringRedisTemplate` Bean**。
- 选 `StringRedisTemplate` 而非现有 `RedisCacheManager`:纯文本存储(可 `redis-cli GET` 直查、无 JDK 序列化二进制 blob)、键名与 TTL 完全可控、避开 `@Cacheable`/`@CacheEvict` 的自调用代理陷阱(见 §5.6)。

## 5. 详细设计

### 5.1 改动范围(最小爆炸半径)

- **仅 `MemorySummaryServiceImpl`**:注入 `StringRedisTemplate`,读路径加缓存、写路径 write-through。
- **`LayeredChatMemory` 一字不动** —— 缓存对它完全透明,它仍只调 `getCurrentSummary(appId)`。这是把缓存放在 Service 层而非装饰器层的核心收益:工具循环、装配、降级路径全不受影响。
- **`MemorySummaryServiceImplTest`**:两个构造器(生产 4 参 `@Autowired` + 测试全参)加 `StringRedisTemplate` 参数。

### 5.2 缓存键 / 值 / TTL

| 项 | 值 |
|---|---|
| key | `mem:summary:{appId}` |
| value | 摘要原文;空串 `""` 表示"暂无摘要",**同样缓存** |
| TTL | 1 小时(具名常量,可调;与 L0 热窗口 TTL 对齐 —— 已核实 `application.yml` 的 `spring.data.redis.ttl=3600` 即 1h) |

**为什么缓存空串(反直觉但必要)**:N+1 放大在"新 app 高强度生成、尚无摘要"期最严重——此时 summary 为空。只缓存正向结果会让这段最热窗口完全不命中。缓存 `""` 把"暂无摘要"也变成一次 Redis 命中,才真正堵住放大。

### 5.3 数据流

- **读 `getCurrentSummary(appId)`**:
  1. Redis `GET mem:summary:{appId}`
  2. 命中(含 `""`)→ 返回
  3. 未命中 → `summaryMapper.selectOneByQuery` → 规整为摘要原文或 `""` → `SET` 回填(带 TTL)→ 返回
- **写 `upsert(...)` 内**(insert 与 update 两分支的 mapper 调用成功之后,在 `upsert` 方法体收尾处统一写一次):`SET mem:summary:{appId} = 新摘要`(write-through,带 TTL)
- **`bumpFail(...)`**(模型失败、摘要未变):不动缓存

### 5.4 降级(延续设计 §13,绝不比纯 MySQL 更糟)

| 场景 | 行为 |
|---|---|
| Redis 读异常 | `catch` → 回退 MySQL(= 现状)→ 返回,不抛 |
| Redis 写异常 | `catch` → `log.warn` → 继续(MySQL 已是真相,下次 miss 自愈),不抛、不拖累异步提炼 |

**铁律:每个 Redis 操作都包在 try/catch 里,缓存层永远不能让事情比"纯 MySQL"更坏。**

### 5.5 已知竞态(可接受、自愈)

"miss 回填 `""`" 与"另一线程 write-through 真实摘要"极小概率竞争 → 可能短暂缓存旧 `""`。TTL 有界 + 下一达标轮次 write-through 覆盖即自愈,落在全局 best-effort 容忍内。不引入分布式锁(过度设计)。

### 5.6 实现注意:自调用代理陷阱

`upsert()` 在同类的 `summarizeNow()` 内被调用(`this.upsert(...)`,自调用)。Spring 的 `@CacheEvict`/`@Cacheable` 靠 AOP 代理生效,**自调用绕过代理** → 注解失效、缓存永不更新。故缓存读写**必须用显式的 `StringRedisTemplate` 调用**,不能用注解。

## 6. 测试策略(TDD)

mock `StringRedisTemplate` 及其 `opsForValue()`,以下 1–6 为**纯 mock 单测**:

1. 命中 → 返回缓存值,`summaryMapper` 零交互(verify)
2. 未命中 → 查 mapper + 回填(verify `set` 带 TTL)
3. Redis 读抛异常 → 回退 mapper、不抛
4. `upsert` 成功 → write-through(verify `set` 写入新摘要)
5. Redis 写抛异常 → mapper 仍更新、不抛
6. 既有 4 个 `summarizeNow` 测试:补 `StringRedisTemplate` mock 保持全绿
7. **(集成层,非单测)** 合并后 `contextLoads`(`@SpringBootTest`,依赖真机 Redis)验证 `StringRedisTemplate` Bean 装配 —— 与前 6 条分层,CI 无 Redis 时不误判

## 7. 待确认前提

`StringRedisTemplate` 为 Spring Boot 在现有 `RedisConnectionFactory` 上自动装配的 Bean(高度确信存在)。若 `contextLoads` 报缺 Bean,则在 `RedisChatMemoryStoreConfig` 补一个基于现有连接配置的 3 行 Bean 定义。

## 8. 风险

- **低**。改动集中单类;读写都有 MySQL 兜底;`LayeredChatMemory` 零改动。
- 缓存与 MySQL **最终一致**(write-through + miss 回填 + TTL),摘要本身 best-effort,无强一致需求。
