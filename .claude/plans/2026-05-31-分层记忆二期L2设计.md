# AI 应用生成平台 · 分层记忆二期(L2 跨 app 用户偏好)设计

## 1. 背景与目标

一期(L0 热窗口 + L1 滚动摘要 + 冷启动重建)已交付并真机验证,直击四痛点中的 1/2/3(长对话失忆、冷启动断裂、token 成本)。本期补**痛点 4 的跨 app 部分**:同一用户下次在**另一个 app** 回来时,AI 仍记得该用户的**通用偏好**(语言、视觉风格、技术倾向等),不必每次重新声明。

对应一期设计文档 §4 四层衰减带中的 **L2 长期记忆**层,§8 与 §15 二期计划。

## 2. 范围边界(仅 USER_PREFERENCE)

一期设计 §8 列了两类 L2 记忆:`USER_PREFERENCE`(用户级跨 app)与 `APP_CONSTRAINT`(app 级硬约束,标注"可选")。

**本期范围:仅 `USER_PREFERENCE`。** 理由:

- L1 摘要已覆盖**单 app 内**的目标/偏好/决策(持久在 MySQL,下次回来即带上)。
- `APP_CONSTRAINT` 是 app 级的,与 L1 摘要的"用户偏好与硬约束"段**职责高度重叠**,不可替代价值存疑。
- `USER_PREFERENCE` 的"跨 app"特性是 L2 **唯一不与 L1 重叠**的价值——这是本期聚焦点。

`APP_CONSTRAINT` 留待真有需要再加(schema 预留扩展位,见 §6)。

## 3. 整体架构与职责切分

### 3.1 L2 在四层衰减带中的位置

`LayeredChatMemory.messages()` 拼装顺序(从最通用到最具体):

```
messages() = [L2 用户偏好·跨app离散条目] + [L1 本app摘要·1对] + [L0 热窗口·原文]
                ↑ 二期新增                   ↑ 一期             ↑ 一期
             按 userId 取 top-N           按 appId            Redis
```

三层各自独立降级:任一层取空,其余层照常注入。

### 3.2 L1 vs L2 职责切分(设计的灵魂——杜绝重叠)

| | L1 滚动摘要(一期) | L2 用户偏好(二期) |
|---|---|---|
| 维度 | per-**app** | per-**user**(跨 app) |
| 形态 | 一段 5 段模板摘要 | 结构化离散条目(多行) |
| 装什么 | 这个 app 的目标/偏好/决策/否决/进度 | 对该用户**任何 app 都成立**的通用偏好(语言、视觉风格、技术栈倾向、交互习惯) |
| 反例 | "这个待办 app 要三档分类"(app 特有 → 留 L1) | "简体中文 / 扁平极简 / 不喜欢大框架"(跨 app → 进 L2) |

### 3.3 关键架构决策

1. **存储形态 = 结构化多行离散条目**(每条偏好一行),对标 Claude Code `memdir` 的离散记忆条目,而非"再做一个 L1 式摘要"。这是 L2 作为长期记忆"可累积、可单条管理、可按需召回"的本质。
2. **`userId` 接线 = service 内反查**。`LayeredChatMemory` 只持有 `appId`(现状),召回时调 `l2Service.recallByApp(appId)`,反查 `appId → userId` 在 service 内完成。`userId` 不出现在 `LayeredChatMemory` 构造器、`AiGeneratorServiceFactory` 签名、Caffeine 缓存 key 中——user 维度的复杂性全部内聚在 L2 service 一处。
   - 依据:`userId` 对 `appId` 是函数依赖(一个 app 永久属于一个 user,`app.userId` 不变),反查是单一数据源,且结果可缓存。
3. **抽取/召回的 user 维度复杂性**全部内聚在新的 `UserMemoryService`。

## 4. 抽取侧(如何从对话识别并落库"跨 app 通用偏好")

### 4.1 触发

复用一期 `doOnComplete` 钩子。两个 Handler(`SimpleTextStreamHandler`、`JsonMessageStreamHandler`)在写完 AI 消息后,除已有的 `triggerSummarizationAsync(appId)`(L1),再加 `triggerPreferenceExtractionAsync(userId, appId)`(L2)。两者皆异步 best-effort,互不阻塞。

### 4.2 游标设计(L2 技术核心)

**偏好归 user(跨 app),但抽取由"某 app 对话结束"触发、扫该 app 的 `chat_history`——故游标是 per-app 的(每 app 独立记"L2 已抽取到哪条"),而产出是 per-user 的(写入 `app_memory(userId)`)。游标维度 ≠ 产出维度,这是 L2 与 L1 最大的不同**(L1 的游标与产出都是 per-app)。

- 新增轻量表 `app_memory_extract_cursor`(per-app 一行),**独立于 L1 的 `app_memory_summary`**——不耦合、不动一期已交付的表与逻辑。
- 扫描**复用一期已建的** `ChatHistoryService.listMessagesAfterCursor(appId, cursor, limit)`,只传 L2 自己的游标值。零新增查询方法。

### 4.3 抽取流程

模型 = `deepseek-v4-flash` 非流式(`@Qualifier("openAiChatModel")`,与 L1 同源)。

```
旧偏好列表(该 user 已有 USER_PREFERENCE) + 游标后的新对话
  → deepseek-v4-flash(判定 prompt)
  → 输出结构化条目 JSON: [{"name":"语言偏好","content":"简体中文"}, ...]
  → 按 (userId, name) upsert 到 app_memory
  → 推进该 app 的 lastExtractedId
```

### 4.4 抽取 prompt(L2 灵魂——防止抽成 app 特有需求)

- **判定标准**:明确指示"只抽取**与具体 app 无关、对该用户任何 app 都成立**的通用偏好;**app 特有的功能需求不要抽**(那属于 L1)"。
- **半封闭 `name` 类别清单**(对标 Claude Code `memoryTypes.ts` 封闭类型系统,保证去重键稳定):
  - `语言偏好`、`视觉风格`、`技术栈倾向`、`交互习惯`、`其他`
  - 指示模型优先归类到上述固定类别,降低"同一偏好造不同 name"导致的重复。
- **滚动**:给旧偏好让模型自行决定"新增 / 更新已有 / 无变化"。
- **输出格式**:严格 JSON 数组 `[{"name": "...", "content": "..."}]`。

### 4.5 去重更新

`(userId, type, name)` 唯一键。抽取输出每条 `{name, content}`:同 name → `update content`;新 name → `insert`。对应一期设计 §8"去重更新"。

### 4.6 降级 / 并发

| 项 | 做法 |
|---|---|
| 线程池 | 复用一期 `memorySummarizationExecutor`(都是记忆后台任务,YAGNI 不新建) |
| single-flight | **按 `userId`**(非 L1 的 appId)——保护 `app_memory` 的 per-user 写,防同用户多 app 并发写冲突 |
| circuit breaker | `app_memory_extract_cursor.failCount ≥ 3` 暂停(同 L1) |
| best-effort | 模型失败 / **JSON 解析失败** → 游标不推进、`failCount++`、不抛异常,下轮重试 |

## 5. 召回侧(`recallByApp` 反查与注入)

### 5.1 messages() 新拼装(在一期基础上最前加 L2,各层独立可降级)

```java
List<ChatMessage> result = new ArrayList<>();
String prefs = l2Service.recallByApp(appId);          // L2(二期新增)
if (StrUtil.isNotBlank(prefs)) {                      // 独立降级:空则不加
    result.add(UserMessage.from("用户跨应用通用偏好…\n" + prefs));
    result.add(AiMessage.from("明白,我会遵循这些偏好。"));
}
String summary = summaryService.getCurrentSummary(appId);  // L1(一期,不动)
if (StrUtil.isNotBlank(summary)) { result.add(U_L1); result.add(A_L1); }
result.addAll(delegate.messages());                   // L0
return result;
```

L2 与 L1 各用独立"前置对",不合并——L2 召回失败返回空串时只是不加 L2 对,L1 照常。两个前置对仍保持 user/ai 严格交替(U,A,U,A,U(L0)…),是一期 §7.5"前置对保交替"手法的延伸。

### 5.2 recallByApp(appId) 内部三步

1. `appId → userId` 反查(查 `app` 表)——**带缓存**(归属永不变,可永久缓存)。
2. 按 `userId` 查 `app_memory` 的 `USER_PREFERENCE`,**按 `updateTime` 倒序取 top-N**(默认 N=10,可配)。
3. 拼成文本返回。

注入格式示例:

```
用户跨应用通用偏好(生成时请遵循):
- 语言偏好:简体中文
- 视觉风格:扁平极简,不喜欢渐变和阴影
- 技术栈倾向:偏好轻量方案,不喜欢大框架
```

### 5.3 缓存(与 L1 完全对称,防工具循环高频放大读)

| 缓存 | key | 读 | 写 |
|---|---|---|---|
| L2 召回结果 | `mem:pref:{userId}` | cache-aside(命中含空串即返回) | 抽取 upsert 后 write-through 刷新 |
| `appId→userId` | 进程内(永久) | — | 首次反查后缓存 |

→ `messages()` 高频路径 = 两次 Redis 命中读(`mem:summary:{appId}` + `mem:pref:{userId}`),不放大 DB。

### 5.4 召回降级

反查失败 / app 不存在 / 查询失败 / Redis 失败 → **返回空串**,`messages()` 只用 L1+L0,**全程不抛异常**(召回在主对话路径,绝不能崩)。

## 6. 数据库 Schema

沿用项目风格:snowflake id + 逻辑删除 + 时间戳。**建表 SQL 必须同时写入 `sql/schema.sql`(本地 init)与 `prod/sql/schema.sql`(生产)**——一期教训:只写 prod 漏了本地,运行库缺表直到真机才暴露。

```sql
-- L2 用户偏好:结构化离散条目,每条一行
CREATE TABLE IF NOT EXISTS app_memory (
    id          BIGINT       NOT NULL COMMENT '主键(snowflake)' PRIMARY KEY,
    userId      BIGINT       NOT NULL COMMENT '用户id',
    appId       BIGINT       NULL     COMMENT '来源 app 溯源(USER_PREFERENCE 可空)',
    type        VARCHAR(32)  NOT NULL DEFAULT 'USER_PREFERENCE' COMMENT '记忆类型(二期固定 USER_PREFERENCE,预留 APP_CONSTRAINT)',
    name        VARCHAR(128) NOT NULL COMMENT '偏好类别(去重键):语言偏好/视觉风格/技术栈倾向/交互习惯/其他',
    content     TEXT         NOT NULL COMMENT '偏好内容',
    createTime  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updateTime  DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    isDelete    TINYINT      NOT NULL DEFAULT 0 COMMENT '是否删除',
    UNIQUE KEY uk_userId_type_name (userId, type, name)  -- 去重唯一键
) COMMENT 'L2 跨 app 用户长期记忆' COLLATE = utf8mb4_unicode_ci;

-- L2 抽取游标:per-app 一行(与 app_memory_summary 同构)
CREATE TABLE IF NOT EXISTS app_memory_extract_cursor (
    id              BIGINT   NOT NULL COMMENT '主键(snowflake)' PRIMARY KEY,
    appId           BIGINT   NOT NULL COMMENT '应用id',
    userId          BIGINT   NOT NULL COMMENT '用户id',
    lastExtractedId BIGINT   NOT NULL DEFAULT 0 COMMENT 'L2 已抽取到的 chat_history.id 游标',
    failCount       INT      NOT NULL DEFAULT 0 COMMENT '连续失败计数(circuit breaker)',
    createTime      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updateTime      DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    isDelete        TINYINT  NOT NULL DEFAULT 0 COMMENT '是否删除',
    UNIQUE KEY uk_appId (appId)
) COMMENT 'L2 抽取游标(每 app 一行)' COLLATE = utf8mb4_unicode_ci;
```

**`type`/`appId` 取舍**:二期只做 USER_PREFERENCE,两列当下无变化值,但保留作低成本扩展位(对标一期设计 §12,未来加 APP_CONSTRAINT 无需 DDL 迁移)。

## 8. 降级矩阵(全程 best-effort,绝不阻塞主对话)

| 场景 | 降级行为 |
|---|---|
| 抽取模型调用失败 / JSON 解析失败 | 游标不推进、`failCount++`、不抛异常、下轮重试 |
| 连续失败 ≥3 | circuit breaker 暂停该 app 的 L2 抽取 |
| single-flight 命中(同 user 在抽取) | 跳过本次(下次补上) |
| 线程池满(拒绝) | DiscardPolicy 丢弃(同 L1) |
| 召回 `appId→userId` 反查失败 / 查询失败 | 返回空,`messages()` 只用 L1+L0 |
| 召回 Redis 失败 | 降级查 MySQL |
| 抽取 insert 撞唯一键(并发) | 转 update,best-effort |

**核心原则**:L2 是"锦上添花",永不是"主对话的依赖"。任何一环失败,最坏结果是"这轮没带上用户偏好",L1 摘要 + L0 热窗口照常工作。衰减带每层可独立摘除。

## 9. 测试策略(对标一期 §14 + TDD 节奏:每组件 RED→GREEN→提交)

- **单测**
  - `UserPreferencePromptBuilder`:含判定标准、半封闭类别清单、旧偏好滚动、结构化输出指令。
  - `UserMemoryService` 抽取(mock 模型):新增 upsert / 同 name 去重更新 / 游标成功才推进、失败保留 / JSON 解析失败降级不抛 / single-flight 并发只跑一次 / circuit breaker。
  - `UserMemoryService` 召回(mock mapper):反查 userId / top-N 排序 / 缓存 cache-aside + write-through / 降级返回空。
  - `LayeredChatMemory`(二期增强):`messages()` 三层拼装顺序 `[L2]+[L1]+[L0]`、L2 空时正确跳过。
- **集成测试**(mock 外部边界、真实串联组件、无需基建——同一期):
  - **跨 app 验证**:user 在 app A 表达偏好 → 抽取落 `app_memory` → 在 app B 召回带出该偏好。直击 L2 唯一不可替代的"跨 app"价值。
- **真机 e2e**(手动、不入 CI,同一期):真实 DeepSeek 抽取 + 真实 MySQL,验证 prompt 判定质量(跨 app 偏好 vs app 特有的切分准确性),哨兵 `userId/appId` 测后清理。

## 11. 风险与开放问题

1. **prompt 判定质量依赖 deepseek-v4-flash**:跨 app 偏好 vs app 特有的切分准确性需真机压测;半封闭类别清单 + 明确判定标准降低发散。
2. **JSON 结构化输出解析可靠性**:解析失败降级为"本次无抽取",但高失败率会让 L2 形同虚设——需日志观测解析成功率。
3. **`name` 去重的语义稳定性**:模型可能对同一偏好造不同 name(如"语言偏好" vs "语言"),导致重复条目。缓解=半封闭类别清单;残余风险存在,可后续加语义归一。
4. **偏好时效与冲突**:用户偏好会变化(先要深色后又否决),靠 `content` 覆盖更新;若模型抽出与历史矛盾的偏好,以最新 update 为准。
5. **召回 top-N 截断**:偏好超 N 条时按 `updateTime` 截断,可能丢失老但重要的偏好。N 可配。
6. **跨 app 配额竞争**:L2 抽取与 L1 摘要、主对话共享 DeepSeek 配额(一期 §16.6 同源问题再叠加一类后台任务);因 best-effort 可降级,通常可接受,高并发为排查点。
7. **`appId→userId` 反查缓存一致性**:app 归属不变,缓存安全;app 删除后缓存残留无害(查不到偏好)。

## 12. 不做什么(YAGNI 边界)

- 不做 `APP_CONSTRAINT`(§2)。
- 不做语义召回/向量化(量小,规则 top-N 足够;一期设计 §8"量大再升级")。
- 不做偏好管理 UI(仅后端记忆能力)。
- 不新建线程池/不新建摘要模型 Bean(复用一期)。
- 不改动 L1/L0 任何逻辑。
