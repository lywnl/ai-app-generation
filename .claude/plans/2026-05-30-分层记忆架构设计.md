# AI 应用生成平台 · 分层记忆架构改造设计

## 1. 背景与目标

当前记忆机制 = Redis + MySQL + LangChain4j `MessageWindowChatMemory`(按条数滑动窗口)。本次改造**参考 Claude Code 的记忆机制**,把"按条数硬截断"的两层结构,升级为"按语义衰减"的**分层记忆架构**。

需解决的四个痛点(已与需求方确认全选):

| # | 痛点 | 当前表现 |
|---|------|---------|
| 1 | 长对话失忆 | 对话超 100 条后,早期需求/约束原文被硬截断永久丢弃,AI 后续"忘记"最初要求 |
| 2 | 冷启动断裂 | 服务重启或 Redis TTL(1h)失效后,只从 MySQL 回填 20 条,上下文骤减 |
| 3 | Token 成本/速度 | 100 条原文全量入上下文,token 成本高、首字响应慢 |
| 4 | 跨会话记忆 | 同一 app 用户下次回来,AI 不记得历史关键决策与偏好(完全缺失) |

**推进方式**:完整设计 + 分期实现(一期 L0+L1,二期 L2)。

## 2. 现状与根因

| 层 | 实现位置 | 作用 | 问题 |
|---|---------|------|------|
| 热层 | `AiGeneratorServiceFactory.java:76-81` `MessageWindowChatMemory.maxMessages(100)` + Redis(TTL 3600s) | 运行时上下文 | 纯按条数硬截断,第 101 条进、第 1 条原文永久丢失,零语义保留 |
| 冷层 | `ChatHistoryServiceImpl.java` MySQL `chat_history` 表 | 全量持久 | 只服务前端分页展示(`listAppChatHistoryByPage`),从不参与 AI 推理 |
| 回填 | `ChatHistoryServiceImpl.java:139` `loadChatHistoryToMemory(appId, mem, 20)` | 冷启动重建窗口 | 只捞 20 条裸原文,重启后上下文断裂 |

**根因**:有全量数据(MySQL)却没有"分层利用"——截断即丢信息,全量却不用于推理,中间缺了"压缩 / 提炼 / 召回"整条带子。

## 3. 参考:Claude Code 记忆机制(源码级)

| 模块 | 源码 | 机制要点 |
|------|------|---------|
| Session Memory(滚动摘要) | `src/services/SessionMemory/sessionMemory.ts`、`prompts.ts` | token 增量 + 工具次数双阈值触发;后台 fork 子 agent 用固定模板滚动更新;总预算 12K/段 2K;直接作压缩的免 API 摘要源 |
| Extract Memories(长期记忆) | `src/services/extractMemories/extractMemories.ts` | 每轮 query loop 结束触发(stopHook);游标 `lastMemoryMessageUuid` 只处理增量、成功才推进、失败重试;主 agent 已写则跳过(互斥);best-effort |
| 四类型分类法 | `src/memdir/memoryTypes.ts` | user/feedback/project/reference 封闭系统;铁律——**只存无法从当前项目状态推导的信息** |
| 智能召回 | `src/memdir/findRelevantMemories.ts` | 轻量 Sonnet 侧查询从清单选 ≤5 条(记忆量小,无需向量) |
| 三层压缩 + Token 预算 | `src/services/compact/*`、`docs/context/token-budget.mdx` | MicroCompact→SM 摘要→API 摘要;按 token(13K buffer)触发;circuit breaker(连续失败 3 次);`CompactBoundary` 只处理边界后消息;tool 对完整性保护 `adjustIndexToPreserveAPIInvariants` |

**核心范式**:记忆不是"存/丢"二元,而是一条"原文→摘要→结构化事实→可检索归档"的衰减带;每层用不同手段在"信息保真"与"token 成本"间取不同的点。

## 4. 总体设计:四层衰减带

| 层 | 装什么 | 持久化落点 | 召回方式 | 期 |
|---|--------|-----------|---------|---|
| **L0 热窗口** | 最近若干轮原文(含完整 tool 对) | Redis(现有 `RedisChatMemoryStore`,TTL 1h) | 全量带入 | 一期 |
| **L1 滚动摘要** | 溢出老对话的语义摘要 | MySQL 新表 `app_memory_summary`(每 app 一行) | 全量带入(1 条) | 一期 |
| **L2 长期记忆** | 跨 app 用户级偏好(+ 可选 app 级硬约束) | MySQL 新表 `app_memory` | 规则取 top-N | 二期 |
| **L3 全量归档** | 逐条原文 | MySQL `chat_history`(现有) | (未来接 RAG) | 现状 |

**`LayeredChatMemory.messages()` 每轮拼装** = `[L2召回(二期)] + [L1摘要·1条AiMessage] + [L0热窗口·原文]`

**关键技术选型**(经 LangChain4j 官方文档确认):
- LangChain4j 原生提供 `TokenWindowChatMemory`(按 token 滑窗,需 `TokenCountEstimator`)——L0 可借其 token 滑窗逻辑,无需自造。
- LangChain4j 内置 **tool 对成对驱逐**:驱逐含 `ToolExecutionRequest` 的 `AiMessage` 时,自动连带驱逐 orphan `ToolExecutionResultMessage`,避免 OpenAI/DeepSeek API 报错。`LayeredChatMemory` 作为**装饰器**直接复用 delegate(`MessageWindowChatMemory`)的此内置能力,**无需自实现**。
- **工具循环依赖 `messages()` 返回结构化消息**(`AiServiceStreamingResponseHandler.java:164-167` `messagesToSend → getMemory().messages()`):故 L0 必须委托给真实 ChatMemory(delegate),而非返回纯文本——这是采用装饰器(方案 Z)而非"文本切片"(方案 X)的根本原因。

## 5. 设计决策汇总(已确认)

1. 目标:四痛点全要 → 完整四层。
2. 推进:完整设计 + 分期实现(一期 L0+L1,二期 L2)。
3. 提炼时机:**异步后台**(复用线程池基建,仿 `runForkedAgent`,对用户透明)。
4. L2 存储/召回:**MySQL 结构化表 + 规则召回**(YAGNI 起步,量大再升级语义召回)。
5. 接入架构:**自定义 `LayeredChatMemory implements ChatMemory`**(记忆逻辑高内聚,单一接入点)。

## 6. L0 热窗口(一期)

- L0 **完全委托给现有 `MessageWindowChatMemory`(delegate)**——`LayeredChatMemory` 是其**装饰器(Decorator)**。
- delegate 负责:保留结构化消息(含 `ToolExecutionRequest`/`Result`)、Redis 持久化(现有 `RedisChatMemoryStore`)、窗口裁剪、**tool 对成对驱逐(LangChain4j 内置,无需自实现)**。
- 窗口大小沿用现有 `maxMessages`(后续可换 `TokenWindowChatMemory` 按 token 管控);默认值实现后压测调整。
- `LayeredChatMemory` 自身**不存储、不裁剪**——唯一新增职责是在 `messages()` 返回前**前置拼接 L1 摘要**(见 §9.1)。

## 7. L1 滚动摘要(一期,技术核心)

### 7.1 触发(何时压缩)
- 在 `doOnComplete` 异步钩子中检查:`估算token(热窗口) > 阈值` 则触发。
- 阈值可配。借鉴 `autoCompact.ts` 的 buffer 思路与 `sessionMemoryCompact.ts` 的保留窗口(`minTokens=10K/maxTokens=40K`,按本项目窗口比例缩放)。
- **仅在"自然断点"(本轮无 pending 工具调用)压缩**,从源头规避切断 tool 对。

### 7.2 滚动更新(增量,非重摘)
- `新摘要 = deepseek-v4-flash(旧摘要 + 这批刚溢出的老消息)`,增量合并而非全量重摘。
- 游标 `lastSummarizedSeq`(用 `chat_history.id` 或 `createTime`)记录"摘要已覆盖到哪条",每次只喂"游标之后、热窗口之前"的消息。对应 Claude Code `sessionMemory.ts:488` 的 `lastSummarizedMessageId`。

### 7.3 摘要模板(5 段,锚定"代码看不出来的信息")

铁律:**只摘代码状态推导不出来的信息**(已生成代码持久化在 `CODE_OUTPUT_ROOT_DIR/vue_project_<appId>`,可随时读取,不进摘要)。

```
# 应用目标与定位            ← 不可推导:初心(用户最初要做什么)
# 用户偏好与硬约束           ← 不可推导:含否定项("不要X"),最易丢失
# 已否决的方案              ← 不可推导:防 AI 重复犯错(代码无"删掉的东西"记录)
# 关键设计决策与理由         ← 不可推导:记理由不记结果
# 当前进度速览(指向,不复制)  ← 轻索引(可选):一两句 + "以最新代码为准"
```

示例(待办清单 app 迭代 60 轮后):

```
# 应用目标与定位
个人待办清单 web app,纯前端单页,移动端优先。
# 用户偏好与硬约束
- 简体中文;扁平极简,禁止渐变和阴影;主色 #4A90D9
- 不要登录注册(localStorage 即可);反复强调加载要快、别上大框架
# 已否决的方案
- 深色模式 → 用户说"太花"撤掉;localStorage 加密 → 用户说没必要
# 关键设计决策与理由
- 原生 JS + localStorage(用户要轻量,故不上 Vue)
- 任务分"今天/本周/以后"三档(用户指定的分类法)
# 当前进度速览
已完成增删改查 + 三档分类;正在做拖拽排序。(代码以 vue_project_<appId> 最新状态为准)
```

固定段落 = 模型滚动更新时只填充/精炼对应段,结构稳定、有职责边界,防发散成流水账。

### 7.4 预算
- 整段摘要 token 上限可配(默认约 1.5–2K,对齐 RAG `prompt.max-context-chars:4000`)。
- 超限让模型压缩,**优先保"应用目标"与"用户偏好与硬约束"**(最不可推导、最该长期保真);对应 Claude Code "优先保 Current State + Errors"(`prompts.ts` 中 `MAX_TOTAL_SESSION_MEMORY_TOKENS`)。

### 7.5 注入与衔接
- 摘要作为 1 条 `AiMessage` 插在 delegate 消息之前(形如"【历史对话摘要】…"),不破坏 user/ai 交替。
- **tool 对保护无需自实现**:L0 由 delegate(`MessageWindowChatMemory`)管理,其内置成对驱逐保证不产生 orphan 工具消息。
- **L0/L1 衔接**:L1 摘要按 `chat_history` 游标覆盖早期历史,delegate 管最近窗口,两者**容忍轻微重叠、绝无 gap**(重叠区为安全冗余),不需要 `ChatMessage`↔`chat_history.id` 精确映射。

### 7.6 提炼执行
- 模型:`deepseek-v4-flash`(与主对话模型同源,快速且成本低,配置参照现有 `chat-model`/`streaming-chat-model`;或新建专用 `summarization-chat-model`),**非流式**。
- 线程池:新建 `MemorySummarizationExecutor`(仿 `ImageCollectionExecutorConfig`,建议 core 5 / max 10 / queue 200)。
- single-flight:同一 appId 正在提炼则跳过(借鉴 `sessionMemory.ts` 的 `markExtractionStarted/Completed` 与 `extractMemories.ts` 的 `inProgress` 标志)。

## 8. L2 长期记忆(二期)

**职责边界**:L1 摘要已覆盖**单 app 内**的目标/偏好/决策(持久在 MySQL,下次回来即带上)。L2 的不可替代价值仅在**跨 app 的用户级偏好**——避免与 L1 重叠。

| L2 类型 | 范围 | 例子 | 召回 |
|--------|------|------|------|
| `USER_PREFERENCE` | 用户级(跨 app) | "极简风/简体中文/不喜欢大框架" | 按 `userId` 取 |
| `APP_CONSTRAINT`(可选) | app 级硬约束 | 太重要、不该被 L1 滚动压缩挤掉的铁律 | 按 `appId` 取 |

- 存 `app_memory` 表。
- 抽取:异步(同 L1 钩子),借鉴 `extractMemories` 的游标 + 互斥 + best-effort;去重更新(`extractMemories.ts:65`)。
- 召回:规则——`messages()` 最前拼 `[userId 的 USER_PREFERENCE top-N] + [appId 的 APP_CONSTRAINT]`;量大再升级语义召回(复用现有 RAG)。

## 9. 组件设计与职责边界

### 9.1 `LayeredChatMemory implements ChatMemory`(装饰器,包裹 delegate `MessageWindowChatMemory`)

## 10. 并发与一致性(零竞态设计)

方案 Z 下并发模型天然清晰——**异步摘要线程根本不碰 `ChatMemory`/Redis**:
- 主线程:AiServices 通过 `delegate.add()` 写 Redis(L0),沿用 LangChain4j 现有行为。
- 异步摘要线程:**只读 `chat_history`(MySQL)、只写 `app_memory_summary`(MySQL)**,推进游标 `lastSummarizedSeq`,不触碰 delegate / Redis。
- `messages()` 在主线程读 MySQL 摘要拼接,摘要更新对下一轮自然可见。

游标是异步提炼与主线程之间的**唯一协调点**(对应 `extractMemories.ts:307` "成功才推进、失败保留重试"),无共享可变状态、无跨线程写冲突。

## 11. 数据流与冷启动重建

一轮对话:
1. 用户消息 → 写 `chat_history`(USER)`AppServiceImpl.java:170` → `LayeredChatMemory.add()`
2. AI 流式生成(上下文 = `messages()` 拼装三层)
3. `doOnComplete`(`SimpleTextStreamHandler.java:36` / `JsonMessageStreamHandler.java:84`)→ 写 `chat_history`(AI)→ `add()`
4. 异步钩子(`MemorySummarizationExecutor`):热窗口超阈值 → deepseek-v4-flash 提炼 → upsert `app_memory_summary` + 推进游标
5. 下一轮 / 冷启动:`messages()` 从 `[MySQL 摘要 + 最近原文]` 重建

**冷启动重建**(解决断裂):`loadChatHistoryToMemory(appId, mem, 20)` 改为"先注入 L1 摘要(`app_memory_summary`)+ 再回填最近 N 条原文(`chat_history`)"。Redis TTL=1h 使其为高频路径,摘要让早期语义不随 TTL 蒸发。

## 12. 数据库 Schema(参照现有 `chat_history` 风格:snowflake id + 逻辑删除 + 时间戳)

```sql
-- L1 滚动摘要:每 app 一行
CREATE TABLE app_memory_summary (
    id              BIGINT       PRIMARY KEY,         -- snowflake
    appId           BIGINT       NOT NULL,
    summary         MEDIUMTEXT,                       -- 5 段模板内容
    lastSummarizedSeq BIGINT     NOT NULL DEFAULT 0,  -- 已覆盖到的 chat_history 游标
    summaryTokens   INT          NOT NULL DEFAULT 0,
    failCount       INT          NOT NULL DEFAULT 0,  -- circuit breaker 计数
    createTime      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updateTime      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    isDelete        TINYINT      NOT NULL DEFAULT 0,
    UNIQUE KEY uk_appId (appId)
);

-- L2 长期记忆(二期)
CREATE TABLE app_memory (
    id          BIGINT      PRIMARY KEY,              -- snowflake
    userId      BIGINT      NOT NULL,
    appId       BIGINT      NULL,                     -- 用户级则为空
    type        VARCHAR(32) NOT NULL,                 -- USER_PREFERENCE / APP_CONSTRAINT
    name        VARCHAR(128) NOT NULL,
    content     TEXT        NOT NULL,
    createTime  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updateTime  DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    isDelete    TINYINT     NOT NULL DEFAULT 0,
    KEY idx_userId_type (userId, type),
    KEY idx_appId_type (appId, type)
);
```

## 13. 降级矩阵(全部 best-effort,绝不阻塞主对话)

| 场景 | 降级行为 | Claude Code 依据 |
|------|---------|-----------------|
| deepseek-v4-flash 提炼失败 | 记日志,游标不推进,L0 不截断(保留更多原文),下轮重试 | `extractMemories` best-effort |
| 连续失败 ≥3 次 | circuit breaker:暂停摘要,回退纯窗口截断(=当前行为) | `MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES=3` |
| `messages()` 读 MySQL 摘要失败 | 只用 L0 热窗口(=当前) | — |
| Redis(L0)TTL 失效/重启 | 冷启动重建:L1 摘要 + MySQL 最近原文 | — |
| 摘要超 token 预算 | 让模型压缩(优先保初心+偏好);仍超则截尾部段落 | `MAX_TOTAL_SESSION_MEMORY_TOKENS` |
| 折叠点切在 tool 对中间 | 推迟折叠到下个安全断点(本轮不压缩) | `adjustIndexToPreserveAPIInvariants` |
| 线程池满(拒绝) | 丢弃本次提炼(下轮再触发),不抛给主线程 | — |

## 14. 测试策略

- **`LayeredChatMemory` 单测**:① `messages()` 拼装顺序(L1 在 L0 前);② `add()` 窗口裁剪 + tool 对成对驱逐(造 `AiMessage`+`ToolExecutionResultMessage` 验证);③ 懒截断(游标推进后跳过已折叠消息);④ `clear()` 只清 L0、保留 L1。
- **`MemorySummaryService` 单测**(mock 模型):① 阈值触发;② 滚动更新 `f(旧摘要+新消息)`;③ 游标"成功才进、失败保留";④ single-flight 并发只跑一次;⑤ 降级不抛异常、不截断。
- **冷启动重建测试**:Redis 空 → 从 MySQL 摘要+原文重建 `messages()`。
- **集成测试**:模拟超窗口长对话,验证老消息进摘要、新消息保原文、上下文连续;VUE_PROJECT 的 tool 对边界不被切断。
- 参考项目已有 `JsonMessageStreamHandlerTest`、`AiServiceStreamingResponseHandlerTest` 测试模式。

## 15. 分期实施计划

**一期(L0 + L1 + 冷启动)**——直击痛点 1/2/3:
0. **Spike 验证**(开工第一步):写最小测试确认装饰器可行——① `LayeredChatMemory` 包裹 `MessageWindowChatMemory` 后,`messages()` 前置一条 `AiMessage` 摘要**不破坏工具循环与 API 消息顺序**(`AiServiceStreamingResponseHandler` 递归取 `messages()`);② delegate 的 tool 对成对驱逐确为 LangChain4j 内置(造 `AiMessage`+`ToolExecutionResultMessage` 超窗口验证)。
1. 建 `app_memory_summary` 表 + entity + mapper。
2. `MemorySummarizationExecutor` 线程池配置。

## 16. 风险与开放问题

1. **摘要质量依赖 deepseek-v4-flash**:5 段模板 + 预算约束降低发散风险;需实际对话压测验证摘要保真度。
2. **token 估算精度**:`TokenCountEstimator` 对中文/代码的估算偏差;热窗口阈值需压测校准。
3. **L1 摘要的 messages() 读取频率**:每轮读 MySQL 有 DB 压力,可加 Redis 缓存(摘要更新后失效)——实现期决定。
4. **Caffeine 缓存的 `LayeredChatMemory` 与摘要更新可见性**:摘要存 MySQL,懒读保证最终一致;若加缓存需处理失效。
5. **窗口/阈值参数**:窗口 token 预算、摘要 token 上限、压缩触发点均为可配项,默认值待一期压测确定。
6. **摘要与主对话共享 DeepSeek 配额**:L1 摘要改用 `deepseek-v4-flash`(与主对话同源),后台提炼会与用户主对话竞争同一份 DeepSeek API 速率配额。因摘要为 best-effort(可降级/重试),通常可接受;但高并发下若主对话变慢,此为排查点之一。
