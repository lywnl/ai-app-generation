## Goals / Non-Goals

**Goals:**

- 让材料选择、摘要提交、原文裁剪和请求投影使用同一份可验证覆盖信息。
- 用不可变请求快照约束 Token 估算与实际发送，并把最新计划读取纳入同一次准备。
- 在既有回合生命周期内完成证据留存、终态关联和异常处理，保持实现可分层验证。

**Non-Goals:**

- 不把新增来源元数据扩展为工具事件数据库或任务恢复引擎；运行对象消失后的能力仍以已确认需求为限。
- 不引入 Redis 与 MySQL 的分布式事务，不改变现有应用租约和部署拓扑。
- 不新增资料管理子系统、决策模型或面向用户的新操作。其他业务非目标沿用 proposal。

## Decisions

### 以持久化用户消息标识回合，为 L0 增加内部来源元数据

对应“原文选择必须保护当前要求和工具配对”“近期原文必须跨回合按 Token 保留”。

使用 `chat_history` 中用户记录的 ID 作为 `userHistoryId`，与运行期 `turnId` 分开：前者连接历史、证据和摘要，后者继续校验当前执行租约。修改用户提交内部调用，使用已有 `addChatMessageAndReturn()`，在原 `commitUser` 边界内保存成功后将 ID 绑定到 `VueTurnContext`，再传入 `TurnRequestBoundary`。不通过“查询最后一条消息”补猜 ID，也不改变对外请求参数。

为 Vue L0 引入内部 `L0Snapshot` 表示，包含：

- `memoryEpoch`：本次 L0 来源集合的标识，冷重建或无法保留原来源关系的重置生成新值。
- 单调消息序号与下一序号：删除旧消息不重新编号；每条消息保留所属 `userHistoryId`，原始 LangChain4j 消息作为 payload。
- 回合描述：运行期 ID、用户消息位置，以及终态可靠落库后登记的 AI 历史 ID 和结束位置。
- 已应用的摘要修订号 `appliedSummaryRevision`：记录这个窗口已省略来源所依赖的摘要修订，作为请求读取所需版本的下界，同时辅助裁剪重试。裁剪和该字段在同一次 Redis 比较替换中提交；冷重建也登记所使用的摘要修订，不能把缺失字段或新 epoch 一律当作零。

这些元数据和原消息保存在同一个 Redis 值中，使用带 `formatVersion` 的封装；消息 payload 继续沿用已有序列化格式。读取兼容旧数组，Vue 新写入使用封装，HTML／MULTI_FILE 保留其现有消息接口。来源元数据在转换成模型请求时剥离，不成为用户消息、系统指令或新的工具消息。

Vue 的追加、关闭回合、按覆盖裁剪及协议恢复分别通过有明确操作含义的 L0 接口更新元数据，沿用 `TokenAwareChatMemory` 和 `AtomicChatMemoryStore` 的共享原子边界。库层提交整份消息数组时不得丢失来源关系，也不得按相同文本给旧消息重新分配 ID。正常追加保留既有序号；破坏来源对应关系的恢复操作使旧待提交草稿失效。

将消息解析成普通消息、完整工具批次和回合结束信息。完整批次由一条含工具调用的 AI 消息及全部对应结果组成，沿用工具 ID、名称、重复结果和缺失结果的校验。可提取现有检查点实现中的纯协议校验，但不保留检查点文字生成。新解析器根据后端登记的结束信息识别已完成回合，不能把任意无工具调用的模型说明当成真实终态。

旧数组在能够与数据库稳定回合边界校验一致时补齐来源关系；无法确认时沿用现有冷重建或受控失败路径。冷重建直接使用查询得到的用户、AI 记录 ID，不从文本反推身份。元数据仅随仍保留的消息及必要回合边界存在，不另存无限增长的序号账本。

取舍：只保存列表下标会在裁剪后错位，用户原文哈希无法区分重复要求；将来源元数据和消息分成两个独立 Redis 写入则会产生半状态。上述封装保留现有消息协议，并让来源关系参与同一次比较替换。

### 单份摘要使用“完整历史游标＋一个部分覆盖前沿”

对应“摘要必须复用并仅合并新增覆盖材料”“摘要与覆盖边界必须一致提交”。

保留 `app_memory_summary` 每应用一行及 `lastSummarizedId` 的原含义，新增以下字段：

| 字段 | 存储约定 | 用途 |
| --- | --- | --- |
| `summaryRevision` | `BIGINT NOT NULL DEFAULT 0` | 摘要正文或覆盖状态的乐观并发版本，成功提交递增。 |
| `coverageVersion` | `INT NOT NULL DEFAULT 1` | 区分旧的完整历史覆盖契约与新的组合覆盖契约。 |
| `coverageState` | `MEDIUMTEXT NULL`，应用层验证 JSON | 保存尚未被完整历史游标吸收的部分覆盖信息；空值兼容旧记录。 |

新的覆盖状态保存部分前沿的 `userHistoryId`、原运行期 `turnId`、`memoryEpoch`、已覆盖消息序号、被覆盖来源前缀指纹及已纳入的证据修订号。回合结束后还可关联真实 AI 历史 ID 和任务终态。指纹覆盖消息身份、原文、工具配对及本次使用的证据，不把摘要文字本身当成来源证明。

部分前沿指向按时间顺序第一个尚未全部覆盖的回合，可能已经结束，不等同于当前正在执行的回合。它之后的材料尚未被摘要覆盖；选择始终推进连续的较早材料，所以不需要为所有历史回合持久化一张覆盖表。当前用户原话即使已作为摘要背景读取，仍受请求层独立保护，不能据此移出当前请求。

将 `MemorySummarySnapshot`、召回契约、压缩结果及持久化接口统一扩展为上述快照。旧格式仍要求有效正文与正数完整历史游标对应；新格式允许完整历史游标为零而存在合法的部分覆盖。空正文、损坏的覆盖信息或超过规格上限的摘要均不能赋予裁剪权限。同一应用的有效生命周期内，修订号只递增，同一修订对应唯一的正文与覆盖状态；后继修订保留或扩展已有覆盖，终态等元数据更新也不能撤销既有覆盖。不同 epoch 的消息序号不得直接比较。

材料构造使用明确的 `SummaryInput`：旧快照及其修订、按序选中的新材料、目标覆盖状态、来源校验信息。历史范围内若有未载入近期 L0 的完整数据库回合，按现有分页方式补齐，不能仅因它们不在 L0 就跨过未覆盖历史。一个回合同时具有 L0 原文与数据库结果时，以来源 ID 合并：已有工具原文采用 L0，终态和决策证据从其权威来源补入，不生成两份完整回合输入。

例如，首轮已摘要至批次 20、随后推进至 35 时，第二次只合并新增批次；该回合落库形成 AI 记录后，只增加结束信息和后续未覆盖材料。只有剩余材料、真实终态及对应证据均被成功纳入，完整历史游标才推进到该 AI 记录，并移除该部分前沿。进入下一用户回合不会自动清空前一回合的部分前沿。

取舍：继续只传 `summarizeThroughId` 无法表示首轮内部进度；把工具批次伪装成聊天记录会破坏冷重建和 L2 游标。组合覆盖保留数据库历史语义，新增字段只表达一份 L1 的来源范围。

### 按摘要修订下界读取相容的 L1 和 L0

对应“请求中的摘要与原文必须完整衔接”。采用版本检测后整对重读，复用 L0 已规划的修订字段，不在数据库与 Redis 两次读取之间持有联合长锁。回合票据只提供生命周期准入，不作为两次读取互斥的证明。

读取成立依赖三个写入不变量：

- 使用摘要修订 r 回收原文时，在同一次 Redis CAS 中更新窗口和 `appliedSummaryRevision=max(旧值,r)`；回收材料必须属于 r 的可靠覆盖。CAS 失败不能单独推进标记，旧回调也不能降低它。
- 冷重建使用哪份摘要跳过历史、建立窗口基线，就将该份摘要的修订和新 epoch 随原文一起写入；清理或协议恢复若继续沿用此前省略的来源，必须保留其摘要依赖。只有经确认没有摘要省略依赖的窗口才允许以零为下界，不能通过换 epoch 清零来放行旧摘要。
- 摘要修订与覆盖遵守上节的单调关系。旧数组先在既有启动／重建入口按稳定历史和所用摘要建立下界；无法证明时沿既有受控失败处理。活动请求不得为了修复读取竞争主动清空原文或伪造旧格式元数据。

统一读取入口返回不可变的 `CompatibleMemorySnapshot`，同时携带 L1 正文及覆盖、L0 原文及来源元数据。一次读取尝试如下：

1. 使用本次请求同一个 `AdmissionDeadline` 和回合许可，从数据库取得完整摘要快照 S。读取使用新的已提交数据库视图，不使用兼容缓存，也不继承较早事务的陈旧读取快照；重试同样重新读取。
2. 通过一次 Redis 快照读取取得 L0 的原文、epoch、来源边界及 `appliedSummaryRevision`。这些字段不得分多次读取后拼接。
3. 核对应用、当前用户来源和快照格式，要求 `S.summaryRevision >= L0.appliedSummaryRevision`，并按持久回合身份及覆盖边界完成来源对齐。修订比较是兼容性的必要条件，不能替代来源校验；旧 epoch 的部分覆盖只能按冷重建规则作为背景，不能裁剪新 epoch 的消息。
4. 如果 S 落后于窗口下界，丢弃本次 S、L0 及派生的候选请求，再从步骤 1 整对读取。来源发生重置时也废弃此前候选并重新对齐；无法证明相容的损坏或未知状态受控失败，不能仅替换摘要正文。
5. 配对通过后固定原文 payload 与来源元数据，将这对快照交给分层视图和后续完整请求组装。分层记忆不得再隐式读取活动 L0 或另取 L1。换用任一快照就废弃此前估算，并重新组装、计量全部请求。

每轮重读沿用现有有界读取执行器、依赖超时和剩余绝对截止，不重置 60 秒，也不触发摘要、裁剪或新的计划初始化。截止耗尽、取消或删除接管后停止重读及后续模型启动，迟到结果丢弃。固定资料继续复用，运行反馈不因重读而再次领取或提前标为送达；最新计划在相容配对后的请求组装中读取。

相容不要求两个修订号相等：

| 捕获情况 | 处理 |
| --- | --- |
| 先读 r1，再读到已按 r2 回收的窗口，且 r1 < r2 | 拒绝这对组合，整对重读；不能让仅由 r2 承接的材料消失。 |
| 读到 r2，但 L0 下界仍为 r1、旧原文尚在 | 可以按 r2 的可靠覆盖投影旧原文；不必等待物理回收，也不重复摘要。 |
| 已捕获 r1 和完整旧 L0，之后后台按 r2 回收 | 在回合及请求代次仍有效时使用已复制的完整旧快照；后台普通回收不修改本地副本，不把后读的新 L0 混进来。 |
| 重读期间 epoch 改变 | 使用新窗口的实际摘要依赖重新准备，不沿用旧序号或旧候选。冷重建、协议恢复和删除造成的来源失效继续受原回合／请求代次规则约束；普通摘要回收的旧副本可用规则不能用于绕过来源失效。 |

上述规则使已回收材料对应的摘要修订成为读取下界，而完整旧原文副本仍然可用。相较于同时持锁跨越数据库和 Redis IO，该方案保留现有短锁和两阶段写入；代价是碰到提交／回收交错时增加只读重试，重试受同一截止约束。

### 在每次请求准备时冻结最新计划和全部请求资料

对应“压缩门禁必须计算完整的实际请求”及计划能力中的“请求预算与实际计划快照一致”。

保留 `ModelRequestGate` 返回不可变 `Decision.messages` 的方式。为 `TurnRequestBoundary` 增加可选的、仅运行期使用的计划快照读取接口，由 Vue Facade 绑定到本应用；不把回调放进 Redis 或数据库。现有初始请求、工具续调和两类协议恢复均已传递该边界，统一由门禁调用读取接口，避免分别拼接不同计划。

计划初始化仍在 `VueTurnContext.initializePlanContext()` 的既有租约边界执行，包括只读回合发生真实修改后的既有初始化入口。请求准备只调用 `AppPlanStateManager.loadReadOnly()`，不调用 `loadForTurn()`。从 Facade 的固定临时资料列表移除计划快照，RAG、图片和 Skill 目录的准备及传递规则保持原样。

一次准备按以下顺序形成 `RequestContextSnapshot`：

1. 在现有请求生命周期内取得上节定义的 `CompatibleMemorySnapshot`，再读取 L2 片段和最新已提交计划。
2. 只从这一对相容快照按已确认覆盖生成历史视图，加入必要的当前可信工程状态和独立保护的当前用户原话，不再单独读取活动窗口。
3. 合并本回合固定资料、本次已领取的运行反馈，以及仅一份当前计划说明。
4. 使用现有估算器对最终消息和工具定义统一计量；此时的快照是阈值判断依据。
5. 如需同步压缩，提交后重新取得相容快照、组装并估算；最终发送只使用获准的不可变快照。

计划格式化继续基于 `AppPlan`，补充文件动作与依赖，并保留同版本内的文件、构建及重新规划状态。每次准备实际读取，不以版本号作跳过读取的依据。“已触达”只描述文件状态，不声明验收通过。格式化中的目标和修订理由保持为计划资料，不赋予其中自由文本额外执行权限。

准备过程中如果换用了更新的计划或其他资料，整个请求重新估算；发送阶段不得再追加未经计量的片段。同步等待期间的重新准备可以再次读取计划，但不再次领取、消费同一反馈，也不叠加固定资料。反馈的有效送达仍由现有请求编排器确认。

读取计划失败沿现有请求准备失败通道处理，并记录内部可识别原因；空计划仅对应成功确认不存在的结果。非 Vue 请求不配置该读取器。

取舍：在 Facade 开始时重建一次计划仍会在长工具链中过期；在模型发送前直接追加最新计划则可能绕开预算。把读取放在门禁准备内，可复用现有所有请求入口和发送快照契约。

### 统一增量草稿生成，保持预算和失败处理的原有边界

对应“历史与当前工具批次必须使用单份滚动摘要”“摘要内容必须保留继续任务所需信息”。

由 `ContextCompressionCoordinator` 选择来源材料，`MemorySummaryDraftEngine` 只负责将旧摘要和选中的新材料生成候选摘要，`MemorySummaryServiceImpl` 负责应用级任务协调及提交。现有只接受完整历史 ID 的内部兼容入口转换成完整历史材料，再进入相同草稿流程；不保留另一套本轮压缩器。

近期窗口从最新完整单元向前选择，使用规格中的 12,288 Token 软目标，独立保护当前用户原话及未完成批次。最新完整批次允许超出软目标。移出候选窗口的原文在提交前仍留在 L0；选择过程不产生提前裁剪。

统一草稿输入将用户消息、模型文本、工具调用／结果、可信终态和决策证据按来源分段引用，不把输入材料作为摘要模型的高权限指令。保留现有五段格式校验和输出缩减机制，调整“当前进度速览”的内容规则。当前状态由真实终态标识约束，后续语义合并再收敛过期诊断，收尾不额外调用摘要模型。

摘要模型的每次输入也必须通过现有输入预算。按完整消息／工具批次组成分块，分块结果仅在本次草稿内增量合并，全部成功后才提交最终正文及整个目标覆盖。单个不可拆单元连同必要提示无法满足摘要输入预算时返回可识别失败，不截断工具结果或把部分成功当成整批覆盖。

异步和同步仍使用规格中的阈值及同一个绝对截止时间。复用已有应用级 single-flight 和执行器，任务携带旧摘要修订、来源快照及启动／提交许可。同步请求加入正在运行的摘要后，重新读取结果，仅对仍未覆盖的材料继续处理，等待和后续处理共享截止时间。

“无新增可压缩材料”与“摘要失败”分开处理：前者沿用现有低于硬上限时可继续的行为；后者沿用同步失败的受控终止映射。已成功压缩但未降到异步阈值以下不等于超出硬上限；最终是否发送仍检查完整请求。达到硬上限且无法容纳必要内容时拒绝发送。

移除 `UnfinishedToolChainCheckpointProjector` 的文字投影、检查点专用重建和准入状态分支。新的复用依据是已经提交的摘要修订与覆盖信息，不能以“本轮已尝试一次检查点”限制后续正常增量压缩。压缩进度继续使用现有对外消息协议。

取舍：按原始 L0 总量判断会重复压缩已覆盖内容；回合收尾固定生成摘要会增加已排除的模型调用。由实际请求触发、由覆盖信息决定增量，直接复用现有草稿与调度能力。

### 先提交可靠覆盖，再按来源比较替换 L0

对应“摘要与覆盖边界必须一致提交”“摘要失败与终止必须保持执行边界”。

提交分为可独立重试的两个阶段，不跨 MySQL 和 Redis 建立分布式事务：

1. 捕获来源快照并确保必要决策证据已可靠留存。摘要模型在数据库事务及 L0 锁之外运行。
2. 草稿完成后重新取得回合提交许可和应用删除栅栏，校验原运行身份、来源前缀及证据修订。选中前缀之后新增消息不使草稿失效；选中来源被修改、替换或失去对应关系则拒绝提交。
3. 在短提交区间按统一锁序取得 L0 来源校验边界、摘要一致性协调锁，在锁内复核来源，并在数据库短事务中核对所用证据的修订。正文、Token、完整历史游标、覆盖状态和递增修订号一次更新；更新条件包括应用、有效记录和期望修订号。首次插入依靠现有应用唯一键，冲突后重读，不盲目覆盖。
4. 数据库确认提交后，在剩余截止时间内使用 Redis 服务端比较替换裁剪已覆盖原文，同时提交来源元数据及不倒退的 `appliedSummaryRevision`。读取侧依据这一标记检查所读摘要能否承接已回收来源；实际裁剪仍保留当前用户原话、未覆盖材料和完整工具配对。

回合提交门与应用删除栅栏位于上述锁序之外；模型调用、长等待和下游模型启动均不持有 L0 或数据库锁。涉及终态登记的路径遵守相同锁序，已有只读摘要路径不得反向取得 L0 锁。保留现有服务端截止检查，不能仅在发出 Redis 命令前检查本地时间。

摘要失败计数和重试时间只更新对应字段，不再通过缺省实体覆盖正文或新增覆盖字段。失败元数据更新也核对修订，避免旧失败回调影响已提交的新摘要。

严格在线请求的每次配对尝试使用一次数据库读取的完整 `MemorySummarySnapshot`，与 L0 校验通过后才返回 `CompatibleMemorySnapshot`；相容性重试允许新的整对读取，不等于混用不同尝试的字段。冷重建同样保存其实际所用摘要的修订依赖。兼容召回缓存改存带版本的完整快照，使用独立于旧纯正文缓存的键；旧缓存不提供覆盖依据。在线准备将相容快照显式传给分层记忆，禁止该层再次召回 L1 或读取活动 L0。沿用既有严格失效顺序，并将新旧缓存键纳入应用删除和失效入口。

| 失败位置 | 状态处理 |
| --- | --- |
| 分块、格式或 Token 校验失败 | 不发布草稿，不推进任何覆盖；保留旧快照和原文。 |
| 许可失效、来源变化或摘要版本冲突 | 丢弃过期草稿，重读有效快照；已结束回合不得继续启动模型。 |
| MySQL 事务失败或提交结果不确定 | 不裁剪 L0；能在截止内确认持久化版本时按确认结果处理，否则沿现有失败通道结束本次准备。 |
| MySQL 成功、Redis 比较失败 | 保留已可靠提交的 L1 和尚在 Redis 的原文。下次准备先按覆盖过滤请求，再校验并重试裁剪，不重新摘要相同材料。 |
| 读取到的摘要落后于 L0 的已应用修订 | 丢弃整对候选，在同一截止内只读重试；失败时受控结束，不清空原文、不重新摘要相同材料，也不沿用旧 Token 估算。 |
| Redis 提交结果不确定 | 不发送未经确认的组合视图；在现有截止处理后重读，不能用旧整窗口写回覆盖晚到的新消息。 |
| 取消、超时或删除已接管 | 旧任务不得提交新覆盖、裁剪后续回合或发送续调；终态保存由原有终态赢家处理。 |

取舍：把 Redis 裁剪失败当成摘要未生成会重复模型调用；用新正文配旧游标则可能丢消息。以 MySQL 的完整快照作为覆盖依据、以 Redis 条件替换作为回收动作，能够保留失败后的可恢复状态。

### 决策证据存入用户记录，并在裁剪前和收尾时增量保存

对应决策证据规格中的来源、实施／验证区分、短回合留存和资源边界要求。

为 `chat_history` 新增可空的 `decisionEvidence MEDIUMTEXT` 字段，保存版本化 JSON。新数据的写入归属于本回合用户记录：它在工具运行前已存在，因此长回合无需提前创建虚假的 AI 终态记录，也不需要临时证据表。旧记录为空时直接按缺失处理。

证据载荷包含格式版本、修订号、用户记录及运行期回合身份，以及有稳定来源标识的条目。条目区分用户原话、AI 正文、计划目标／用途／修订理由，保留必要原文或可解析的持久原文引用、generation、文件／工具引用、已提交执行依据和验证状态。用户原话可引用同一用户记录的 `message`；裁剪后无法从其他持久来源还原的 AI 解释必须保存必要原文。

采集不承担新的语义模型推理：收集已有转录和计划材料，把“是否构成关键决定及其理由”的提炼留给统一摘要。只有明确关联的原始表达和可信执行依据才能标成已实施；仅在同一 generation 出现过工具成功不能证明所有建议都已采用。无法关联的模型说明保留为未确认历史材料，构建失败和文件已经修改分别记录。

将转录与可信事实的只读访问纳入 `VueTurnContext` 的回合共享采集组件。复用现有 `VueTurnTranscriptAccumulator`，不复制一份无界转录。执行链登记可用于后续请求的消息和事实时，同时登记来源引用；准备裁剪时须确认该批次的采集边界已到达，不能依赖下游 SSE 展示消费恰好完成。计划工具成功提交时保留原始目标、用途和修订理由的引用，避免只读取已经截短的最新计划历史。

保存时机为：

- 压缩准备将回收相关来源前，保存截至该边界的必要证据；保存失败则该来源仍不可回收。
- 回合收尾时合并最终新增证据及实施、验证状态，即使该回合没有触发摘要也执行。

以条目来源 ID 合并重复采集，每个条目记录最近变化的证据修订号。已经引用的原文不因状态更新重复累加副本；摘要只读取上次证据覆盖之后新增或发生状态变化的条目。数据库通过用户记录短事务串行合并，校验应用、用户归属和既有载荷修订，不能让迟到快照覆盖更完整的证据。

正文留存沿用现有输出资源限额，元数据与引用同样做有界校验；工具展示、完整日志和源码不作为整份转录额外复制。限额或保存失败不得通过静默丢弃必要依据来宣称来源已可回收，继续使用既有资源限制及失败处理。

`decisionEvidence` 不拼入 `memoryMessage`，不进入 L2 抽取输入或服务端验证状态。历史接口保持原响应，新增字段使用明确的对外序列化排除；授权内的摘要与重建通过内部读取接口访问。删除随所属聊天记录清理。

取舍：只写最终 AI 记录无法在首轮中途裁剪前持久留存；把解释拼入可信记忆会混淆来源。用户记录提供现成的稳定身份和生命周期，独立字段满足提前留存及短回合要求。

### 收尾只登记结束与可信结果，请求投影保留合法原文

对应“可信工程结果必须独立保留”“已覆盖的历史结果不得重复独立注入”。

`VueTurnFinalizer` 继续使用现有终态单赢家机制及 `VueTurnMemoryProjection`。最终证据合并、AI 展示／可信结果保存和必要的摘要任务状态登记置于同一短数据库提交边界；回合结束状态只标记真实终态，不推进尚未语义覆盖的来源位置，也不发起摘要模型调用。

若该回合正是摘要部分前沿的所属回合，登记其 AI 历史 ID 和真实终态并递增摘要修订，防止旧异步草稿把它重新标为执行中。登记终态前后均不得把已有工具前缀重新当作整轮新材料。下一次请求使用后端终态标识约束旧摘要中的进行中描述，后续正常增量摘要再合并新增终态。

MySQL 成功后，合法完整回合通过 L0 关闭操作登记结束位置并保留工具调用、结果和必要说明。后端终态使用内部类型及持久化 ID 关联，不靠匹配模型文字中的“成功”或某个标题识别。原 `ToolMessageCollapser` 的无条件正常收尾调用退出；不完整或非法工具链继续走既有丢弃、恢复和终止分支。MySQL 或 L0 同步失败时保留现有终态反馈、失效与冷重建规则，不能把错误表示为新的成功结果。

`TrustedTurnRequestViewProjector` 改为接收已选定的覆盖快照与带来源的消息视图。处理顺序为：排除已覆盖且不受原话保护的材料，分离明确来自后端的终态表示，保持其余消息的工具配对、次序及回合归属。语义摘要仍通过现有历史资料通道注入。

必要的当前工程状态由运行期可信状态及必要的最近真实终态构造为一份说明，计入预算；不再遍历所有旧回合追加结果文本。仍在近期窗口的工具结果完整保留。已经被 L1 覆盖的独立历史终态不再注入，未覆盖终态也不能同时以原终态正文和独立投影重复出现。状态来源在内部区分后端结果与模型解释，不能凭角色名称把普通 AI 文字升级为可信事实。

L0 合法关闭后，L2 仍以真实保存的稳定 AI 记录 ID 进入既有提取入口，独立证据不改变其职责。软 Replan、构建反馈和只读升级反馈沿原送达机制保持临时性，不落普通历史。

取舍：只停掉回合折叠仍会被请求投影清空；只停掉请求投影则无法找回已删除原文。收尾与投影共享来源和覆盖模型，才能同时保证存储与实际请求可继续使用近期过程。

### 兼容适配与验证沿真实读写边界组织

对应“旧历史与冷重建必须保持兼容边界”及已有构建、修改升级规范。

冷重建保留工厂从完整历史加载的行为，扩展读取独立证据和新摘要快照。新运行对象生成新的 `memoryEpoch`，并把实际用于重建的摘要修订写入 `appliedSummaryRevision`，同原文一次提交；换 epoch 不清除窗口仍然需要的摘要依赖。旧部分前沿的摘要正文可以作为历史背景，但其消息序号不赋予裁剪新 L0 的权限。旧任务没有结束记录时仍走现有孤立用户回合修复，不恢复工具执行。修复成功后，以已确认的旧用户记录 ID 关联补写的真实终态，并通过同一结束登记规则更新对应摘要状态，不能把它绑定到新用户回合。

对于已有部分摘要但工具原文已不可恢复的回合，使用持久化用户身份、证据修订及真实终态对齐可用历史。已覆盖证据不作为新增材料重复合并，未覆盖终态仍需处理；缺失工具轨迹不伪造。完整历史覆盖只能基于实际可用的持久历史表示推进，不用旧 epoch 的序号假定新消息已经覆盖。

HTML／MULTI_FILE 的历史输入通过完整回合适配进入共享快照接口，不配置 Vue 计划或决策采集组件；独立评估链保持隔离。旧五段摘要、已折叠历史和空证据继续读取。协议恢复、取消与删除由现有入口控制，不新增后台恢复任务。

验证落点围绕接口行为组织，具体执行任务留给 tasks：

| 验证层 | 重点及现有落点 |
| --- | --- |
| 来源解析与覆盖 | 相同用户原文的不同回合、并行工具完整配对、首轮游标零、部分前沿跨回合保留、三次增量覆盖；扩展现有解析器、窗口、快照和草稿引擎测试。 |
| 真实请求组装 | 初始、续调及恢复入口捕获最终请求，验证最新计划、同版本更新、资料各一份、预算与发送一致；复用门禁及 Facade 测试入口。 |
| 收尾与跨回合 | 同时读取 Redis L0 和下一次模型请求，证明近期原文未被两次投影移除；检查已覆盖旧结果不逐轮出现，并核对可信终态和 L2 触发。 |
| 决策与信任 | 未压缩短回合、裁剪前存证、无依据理由、未执行建议、已修改但构建失败、重复采集和存证失败；核对原文、证据字段及可信结果分别读取。 |
| 并发和故障 | 来源只追加／被修改、终态先取得边界、摘要 CAS 冲突、缓存失效失败、分块失败、事务失败、Redis 结果不确定、取消和删除期间迟到回调；验证无越界裁剪及后续模型启动。 |
| L1／L0 读取交错 | 请求读 r1 后暂停，后台提交 r2 并回收，再恢复读取；兼顾新 L1＋旧 L0、完整旧副本捕获后回收、epoch 重置、重读截止及取消。分别检查配对结果与最终实际请求，证明无材料缺口、重复摘要、旧估算复用或迟到发送；纳入真实 MySQL／Redis 组合验证。 |
| 迁移与兼容 | 两份初始化 schema、增量迁移重入、旧数据、旧 Redis 数组、冷重建及接口不暴露新字段；兼顾原有构建保护和只读升级回归。 |
| 真实验收 | 使用真实 MySQL／Redis 验证事务、比较替换及迁移；按已确认需求执行含否定约束、计划变化与构建修复的真实模型长任务，连续三次压缩并记录实际请求证据。 |

已有 `MemorySummarySnapshotIntegrationTest` 等测试包含替身装配，不能仅凭名称代替真实数据库或模型证据。监控扩展现有压缩指标，记录快照复用、原文量、覆盖和去重结果；不记录原始用户内容、完整源码或工具正文。

取舍：只检查摘要文本无法发现请求侧二次删除；只检查本地替身无法覆盖真实事务和 Redis 截止行为。验证需要覆盖生成、持久化、裁剪及发送这几个实际边界。

## Risks / Trade-offs

- [来源元数据改造涉及 L0 的所有写入口] → 追加、收尾、系统消息替换、协议恢复、冷重建和清理统一保留或明确重置来源；用实际存储与请求双向回归验证，禁止静默重新编号。
- [单份摘要的部分前沿在回合结束后被误清空] → 前沿以持久用户身份关联，结束只更新状态，完整覆盖后才归并到历史游标。
- [异步摘要与终态保存互相覆盖] → 数据库修订条件、来源校验和现有回合门共同约束；终态状态更新使旧草稿失效。
- [MySQL 已提交而 Redis 未完成裁剪] → 保留原文，以已提交覆盖生成请求并幂等重试裁剪；不新增模型调用补偿存储失败。
- [请求把旧 L1 与已经回收的新 L0 混用] → 省略原文与读取下界同次提交；请求校验修订和来源后才固定整对快照，不相容时在原截止内整对重读，分层组装不再读取活动窗口。
- [决策采集落后于执行链，或把同批建议都当成已实施] → 使用与来源提交对应的采集边界和明确事实引用；缺少关联时保持未确认，不给裁剪或验收结论。
- [近期工具原文与部分前沿元数据增加 Redis 占用] → 只在已确认覆盖后回收，元数据随保留窗口清理，单批超限沿既有门禁处理；不承诺重启恢复整段工具轨迹。
- [旧版本程序不能理解新覆盖状态] → 发布时避免新旧写入器混用；回退版本必须支持新快照，不能直接用旧完整游标逻辑覆盖新记录。
- [真实长任务的语义保留质量无法由格式校验证明] → 保留既定真实模型验收，检查约束、失败尝试及计划新鲜度；本设计不承诺摘要无损。

## Migration Plan

1. 在现有两份初始化 schema 及新的增量脚本中增加摘要修订、覆盖版本／状态和独立证据字段。增量脚本沿用 MySQL 8.0.40 的条件加列、重入检查和元数据验收方式；明确 DDL 隐式提交。新脚本使用独立文件，保留现有迁移及其数据修复逻辑。
2. 旧行保持 `coverageVersion=1`、`summaryRevision=0`、空覆盖状态与空证据，不改写历史正文，不补造理由或工具轨迹。应用读取时适配旧契约，首次成功提交新覆盖再写入新版本。
3. 在部署新写入路径前停止新回合进入并按现有生命周期等待或结束在途回合；新旧程序不得同时改写同一应用摘要或 L0。Redis 原数组在来源对齐后建立所需摘要下界，新的 Vue L0 在已有键内使用版本化封装；不对未知下界默认填零。摘要缓存使用新版完整快照键，删除与失效入口同步覆盖。
4. 上线检查使用迁移元数据、旧记录读取、新回合及跨回合请求证据确认结果，再恢复正常进入。数据库迁移和真实服务操作在实施及发布阶段执行，本设计不执行这些操作。
5. 仅加列而尚未写入新格式时，可回退程序并保留新增列。已经存在新覆盖或 L0 封装时，回退到保留新格式读写兼容能力的修复版本；不能直接部署只认识旧游标的版本。紧急关闭生成后可从持久历史按既定冷重建能力恢复 L0，但不得宣称未摘要工具轨迹可恢复，也不得删除新摘要或证据来伪装旧格式兼容。

上述技术选择均落实既有需求，无需新增业务决定。类名和私有方法拆分可在实现中调整，来源身份、覆盖语义、提交顺序、信任边界及上述回退限制作为实现约束。
