# Design

## Context

基线 `fc4685e` 使用独立 Attachment/afterSequence；L0 版本 1 只有真实 Message，来源构造器不允许额外用户消息。Redis CAS 以旧快照编码比较，原文解析器和协议恢复依赖原消息列表。直接把恢复正文作为普通 UserMessage 追加会伪造来源并污染覆盖，因此扩展窗口类型。

## Decisions

### 1. 一个窗口，两种来源

L0 有序 entries 扩展为封闭类型：ORIGINAL（保留 Message 及所有来源字段）和 PLAN_RESTORE（restoreId、计划 ID/版本/定义指纹、覆盖键、不可变正文）。应用/epoch 由父快照约束，恢复没有 sequence/userHistoryId/historyRecordId。构造和 codec 拒绝未知类型、不合法身份及重复恢复。显式 originals/originalMessages 供摘要、协议、计数、指纹与证据使用；恢复投影仅用于实际模型请求。

来源 parser 只处理 ORIGINAL；恢复条目位置直接取有序窗口，不再持有 afterSequence。投影依次处理来源单元和恢复条目，保留可信终态分离及冷重建轻量确认；原用户计数不看恢复的 User/Ai 包装。原模型字符串不能变成内部类型。

### 2. 可靠边界与原文回收

覆盖键沿用 lastSummarizedId 加部分前沿的 userHistoryId/turnId/epoch/coveredSequence，排除 summaryRevision 和终态登记字段。prune 在覆盖改变时撤下恢复条目；其余按原规则回收真实来源。仅添加/删除恢复条目不推进 appliedSummaryRevision，不分配原文序号，也不能成为回收授权。fingerprint、containsPrefix、决策证据和摘要预算仅使用 ORIGINAL。

协议恢复从显式原文视图构造 replacement，epoch 改变清除旧恢复条目。正常结束保留窗口及恢复资料；冷重建仍只导入持久完整历史，建立新 epoch 后按需恢复。

### 3. 编码升级与停机降级

键不变，formatVersion=2 区分两类条目；v1 解码保留版本且按 v1 重新编码作为 CAS expected。候选以 v2 编码，原子比较成功后升级。旧数组保留现有来源未知/冷重建路径。逐条编码 payload，不使用展开消息与 entry 的下标对应假设。

新旧进程不得同时写同一键。交付仅接收显式应用 ID 的降级命令/操作入口；操作前要求停止写入，读单键、验证应用、去掉恢复、以精确旧值 CAS 回写 v1，保留 TTL/原文/epoch/依赖；没有窗口时报告无操作，未知或损坏数据拒绝，无 KEYS/SCAN 或清空路径。真实 Redis 验证 v1→v2、冲突保留、降级及旧 codec 等价读取。降级工具是维护入口，不自动运行于业务键。

### 4. 同步定义标记与按事件检查

服务端计划管理器在 save 成功及计划外新增路径成功落盘之后，同步更新应用的定义变化代次与定义身份（ID/版本/指纹）；不保存计划正文，不依赖 SSE。普通状态、构建状态及 loadForTurn 不触发。请求边界绑定只读计划能力和无 I/O 的定义变化读取能力；应用记忆仅保存已检查代次、epoch/覆盖及待检查原因。

首次加载/新实例、epoch 或可靠覆盖变化、定义事件触发检查。已知最新定义事件时先匹配完整成功工具批次，可免读盘并撤下恢复；无可用事件身份的首次检查读盘核实。已有匹配恢复按原 ID、正文、位置沿用，否则只读当前磁盘计划并生成一份。读不到计划是已检查的无计划状态，读失败不是无计划。未完成批次不得当完整结果，必要时保留待检查标记，批次完整后重新判定。普通续调不扫完整计划或额外读盘。

定义值比较含身份、版本、目标和完整文件定义；路径与依赖排序消除顺序噪声，排除运行状态。指纹是服务端确定性计算，原工具结果仍核对调用/结果配对、operation、APPLIED 和非空合法文件定义。

### 5. 一次插入与事务门禁

恢复候选插在最后一个完整、可见、非终态原文单元之后；不能插入调用/结果之间，后续原文自然追加。真实覆盖推进后旧恢复无效，按新窗口恢复当前计划，其他场景不移动已有条目。

请求准备先取得相容快照，完成恢复所需读盘，再在现有应用 writer、回合提交门、绝对截止与 L0 CAS 下提交窗口及检查代次。CAS 冲突在原截止内重读，按实际窗口幂等；取消/删除/失效或变更代次改变拒绝迟到候选。慢读盘和 Token 估算不持回合票据；Redis 提交沿用有界截止。恢复提交成功后才冻结/计量/发送，最终发送仍经原回合门。同步压缩等待恢复；异步压缩只影响后续准备，不修改已冻结请求。

### 6. 快照语义与预算

复用既有 recoveryBody：版本、目标、计划级状态、必要修订及每文件一行定义/状态，明确 TOUCHED 不代表验证成功。UserMessage+固定 AiMessage 确认仅在 API 投影展开，不伪造工具身份。整个冻结请求包含恢复资料预算；原文 12,288 Token 配额、L1/L2/RAG 行为与超限失败保持。

## Risks / Trade-offs

- Redis 每次原文追加会重写更大的快照；以真实字节数报告，不预设节省比例。
- 不做手动改文件实时感知；依赖所有服务端定义写入点的同步事件，单测覆盖正常 save 和计划外路径。
- v1/v2 混合写不受支持；上线按停写切换，回退先显式降级。没有新增表/键，但属于持久化格式迁移，strict 真实验证不可省略。
- API 包装增加消息数但不增加真实用户回合；来源校验必须基于类型。
- 不承诺服务重启续跑；新实例继续现有冷重建。

## Validation

窗口/codec/CAS/降级、来源/指纹/裁剪/摘要/证据/协议恢复、定义事件和请求门禁单测；完整/并行/未完成批次；同步/异步/连续压缩、失败和仅终态修订；跨回合/应用、冷实例、取消删除、并发追加和迟到读盘。真实 Redis 加隔离 MySQL 验证编码迁移和兼容摘要；模型替身执行真实 Java 流“创建→写入→修订→压缩→恢复→续写→构建”。比较读盘次数、恢复次数、请求 Token 与 Redis 字节数，捕获实际请求证明计量一致；恢复不进入摘要/证据。原始日志位于 `.codex/plan-restore-l0/`。

## Migration Plan

本轮实现并测试升级及降级能力，不操作业务键、不重启、不部署、不提交。旧规划和报告原字节保存在 `history/fc4685e/`；本轮独立评审、实施入口和验收使用固定当前报告，不借用旧 PASS。
