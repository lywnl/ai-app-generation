# Design

## Context

现状及范围见 proposal。`UnifiedContextRequestPreparer.prepare` 先取得相容 L1/L0，再无条件追加 `formatPromptContext(plan)` 和合成确认消息。`TrustedTurnRequestViewProjector` 会先应用可靠覆盖，再拆出后端终态；因此扫描 Redis 全窗口或最终消息的字符串都不能证明计划真正可见。`L0SourceParser` 已提供完整工具批次和不可复用的来源序号，可直接用于判定与锚定。

`.plan.json` 通过既有只读边界读取；普通文件成功变更只更新状态，不递增计划版本。服务按应用缓存，每个服务有独立 `CompressionAwareChatMemory`，适合承载不持久化的附件。现有合成记忆协议提供 `PLAN_SNAPSHOT_ACK`，普通原文与摘要来源有独立边界。

## Goals / Non-Goals

- 复用同一相容快照完成可见性判定、附件定位和请求投影，避免判定与实际发送来源分离。
- 附件状态修改为短时原子内存操作；计划读取、L2 召回与 Token 估算保持在回合票据之外。
- 不修改 L0 编码、摘要覆盖算法、计划工具输出或文件工具通知；不引入全局缓存、持久化格式及新的通知通道。

## Decisions

### 1. 用定义值对象识别完整计划

新增后端内部计划上下文组件，从不可变 `AppPlan` 与成功 `PlanToolResult` 构造定义值对象：计划 ID、版本、目标、按路径归一比较的文件定义，依赖按集合语义比较。排除文件状态、计划级执行状态、活动回合绑定等运行进度；新增计划外路径属于文件集合变化，仍触发定义不匹配，并保留既有 Replan 反馈。

只检查可靠覆盖后的 `L0SourceParser.Kind.TOOL_BATCH`，同时验证真实调用名称、配对结果名称及协议 `operation`、`status=APPLIED`。需要完整非空文件定义；自由文本、失败结果、摘要及 pending 批次均不能充当证据。复用既有严格解析器，解析不成立只意味着没有成功计划证据，非法工具链仍由现有解析失败通道处理。

不采用仅版本或“已发送”布尔缓存，因为它们分别遗漏同版本定义变化和上下文淘汰。

### 2. 附件为应用记忆实例中的独立不可变状态

`CompressionAwareChatMemory` 持有一个原子状态引用，状态包含可空附件及用于识别失效／并发更新的状态代次。附件包含应用、定义、epoch、覆盖键、锚定来源序号和已格式化正文。每次解析返回候选状态；最终准备完成后，在有效回合票据及应用生命周期许可内，校验所捕获代次并提交。附件失效会变更代次，迟到准备不得覆盖它。生产记忆清空继续由 `AiGeneratorServiceFactory.invalidateAndClearMemory`／`prepareVueColdRebuild` 显式失效服务并清除来源，新记忆实例从空附件状态开始；不得绕过 `TokenAwareChatMemory.clear()` 对已对齐来源的既有拒绝。

附件正文只存在于该内存对象和冻结的请求中。模型接口序列化沿用服务端合成资料消息与 `PLAN_SNAPSHOT_ACK` 包装，正文明确说明不是新用户指令；不调用 `memory.add`，不分配来源序号，不写普通原文、历史或摘要输入。

### 3. 覆盖键独立于摘要修订号

覆盖键由 `lastSummarizedId` 和部分前沿的用户来源、epoch、`coveredSequence` 构成；不使用 `summaryRevision`、`terminalHistoryId` 或仅登记终态产生的字段变化。相同覆盖下物理回收不改变附件；实际覆盖键变化后重新选择当前可见计划，必要时恢复新快照。

epoch 改变直接使旧附件失效。锚点必须仍属于实际可见的完整非终态来源单元；锚点缺失或不合法时不盲目挪动旧正文，而是重新恢复。这样既处理冷重建，也不把回合结束等价为压缩。

### 4. 在来源单元边界插入附件

从恢复时最后一个完整、实际会投影的原文单元记录 `lastSequence`。投影器完成既有可信状态分离后，在对应单元之后插入附件，保留原文与工具批次的原顺序。合成历史确认消息的处理继续按真实原文计数，不能因附件存在而改变用户回合识别；服务端附件也不能出现在可信状态的原始用户回合列表。

后续请求重用相同锚点；新增工具结果排在其后。pending 工具批次不作为锚点，不在调用与结果间插入。新的匹配成功计划结果优先于附件，直接使旧附件撤下。

### 5. 专用恢复正文保持快照语义

新增专用格式化逻辑，不全局更改可能供既有反馈使用的 `formatPromptContext`。正文包含计划 ID／版本、目标、恢复时计划级状态、最近必要修订原因；每个文件一行列路径、用途、动作、依赖和恢复时状态。声明后续工具事实与服务端状态优先，`TOUCHED` 仅代表发生修改。沿用已有计划不得重复创建、需要调整调用 `updatePlan` 的提示，不根据旧快照状态制造新的写入阻断。

### 6. 一份最终请求统一计量与发送

保留既有 `readLatestPlan`、读失败、截止、取消及删除检查。每次读取前捕获附件代次，读取后再次检查有效性；最终由当前相容历史、候选附件、L2／L1 和已领取临时资料形成冻结消息，再估算 Token。所有入口继续经过 `UnifiedContextRequestPreparer`，同步摘要后重新准备，异步只使用当前已捕获的相容请求，下一次请求观察新覆盖。

缓存提交前复检回合、截止和应用栅栏；代次失效受控失败，不把迟到读取当作新请求。缓存持有可恢复正文不代表反馈已经送达，现有送达确认机制保持不变。

## Risks / Trade-offs

- 历史快照进度落后于磁盘 → 明确快照语义与插入顺序，保留现有工具结果和 `currentRequestState()`；不新增通知。
- 判定扫描与投影使用不同来源 → 共享可见来源计算入口并对覆盖已提交但回收失败的情况测试。
- 冷重建或摘要之后重复遗漏计划 → 附件持有正文，并测试多次后续请求及连续覆盖推进。
- 并发清空、取消、删除使慢读取迟到 → 捕获内存状态代次，提交使用现有生命周期边界；慢 I/O 不持有回调票据。
- 缓存不跨服务实例持久化 → 冷实例允许一次重新恢复；不保证服务重启恢复进行中的生成。
- 计划本身仍有 Token 成本 → 只统计额外附件数量，受控 E2E 比较相同输入下旧追加方式与新实际请求，不预设比例。

## Validation

- 单元／门禁：成功与伪成功来源、同版本定义与状态、完整及 pending 批次、固定锚点、summaryRevision 与真实覆盖、跨回合、清空、epoch、跨应用、读失败、取消及删除。
- 捕获真实 `StreamingChatModel` 的 `ChatRequest`，断言消息与估算输入相同、附件最多一份、原始计划参数与结果不变，摘要输入与 L0 无附件。
- 受控端到端驱动实际 Java 流式门禁、计划／文件工具及构建检查；模型为本地替身，原文存储为来源感知内存实现，文件和 `.plan.json` 使用 `.codex/reuse-plan-context/` 下隔离目录。摘要和构建使用项目可控测试入口，明确替身边界并验证真实来源覆盖与构建门禁，不调用线上服务。
- 运行相关记忆、计划、文件工具、构建及恢复回归；日志、JUnit 和 Token 比较保存在 `.codex/reuse-plan-context/`。独立实现评审及结构化证据核验作为交付条件。

## Migration Plan

不需要数据库或 Redis 迁移。交付为普通后端代码变更，实例更新后按需恢复附件；回退相关代码即可恢复旧请求组装方式，已有磁盘计划、L0、L1 格式和旧验收记录不变。本轮不启动、部署或重启服务，不自动归档变更。
