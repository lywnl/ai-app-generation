## 发现与处置

### IR1：旧版零修订摘要可能使计划判定与最终可见历史不一致（P2，已关闭）

- 位置：`TrustedTurnRequestViewProjector.visibleSource()` 与 `PlanContext.select()`。
- 根因：初版共用入口只在 `summaryRevision > 0` 时执行可靠裁剪；投影器仍单独排除完整历史游标已覆盖的闭合回合。合法旧版摘要 `summaryRevision=0`、`lastSummarizedId>0` 下，计划判定能看到将被最终投影排除的旧 `makePlan` 成功结果，错误省略恢复附件。
- 影响：实际发出的请求既没有完整旧计划结果，也没有恢复附件，违背按实际可见历史判断的要求。
- 修复：已把闭合回合的完整历史游标过滤移入共享 `visibleSource()`，投影器不再单独追加不同的过滤规则。
- 关闭证据：新增 `PlanContextTest.旧版零修订摘要隐藏的成功计划也必须按实际可见历史恢复`，保留旧原文并构造真实合法旧摘要，断言当前请求恢复附件且不发送旧工具结果。已复核源码；`e2e-02` 中该类 32 项通过，最终 `regression-01` 再次全部通过。

未发现第二个需要修复的正确性、可信来源或生命周期阻塞。

| 定义与进度 | 定义含 ID、版本、目标、文件路径／用途／动作／依赖；文件与依赖顺序归一，排除触达、构建状态和活动回合绑定。普通状态变化复用原正文，新定义或完整新版成功结果分别重建或撤下附件。 |
| 覆盖与来源 | 覆盖键使用完整历史游标及部分来源身份／epoch／序号，排除 `summaryRevision` 和仅终态登记字段；物理回收不制造新恢复。共享来源过滤同时覆盖当前版本和旧版摘要。 |
| 附件位置 | 锚点只来自完整非终态原文单元。投影完成原始用户顺序及冷历史确认后，再在对应位置插入资料对；新工具消息在旧附件之后，不把附件插入调用和结果之间。 |
| 原文与摘要隔离 | 附件只在实例字段和冻结请求中存在，未调用原文追加或持久化接口；L0 编码、摘要选择、覆盖与回收逻辑未增加附件来源。正文使用明确服务端资料语义及既有合成确认标记。 |
| 取消、终态与删除 | 捕获状态引用在读计划之前，短提交使用当前应用 writer、回调票据及 `commitSummaryWhileActive`。后者按既有 app 租约 → 终态提交门定序并检查截止，提交内再次检查应用栅栏，CAS 拒绝失效代次；所有计划 I/O、L2 召回和 Token 估算均在票据之外。 |
| 冷重建与应用隔离 | 附件属于具体记忆实例；应用、epoch 与锚点被核对。工厂显式失效／重建继续产生新实例。普通 `clear()` 先失效附件但仍保留已对齐 L0 的原有拒绝，不借此删除来源或丢失摘要依赖。 |
| 预算与发送 | 先选择附件并完成分层投影，合入既有临时资料后冻结列表，再计量；初始、续调、同步重组和恢复继续使用同一门禁。实际模型替身捕获的 `ChatRequest` 与估算消息、工具定义相同。 |
| 公开契约 | 没有修改 API、SSE、计划／文件工具协议、摘要提示词、窗口／阈值、前端或持久化编码。现有 Replan、构建反馈和 `currentRequestState()` 保持各自通道。 |

`commitSummaryWhileActive` 在这里仅用于复用已有的取消／终态提交门，闭包只做栅栏复检与内存 CAS，不生成或提交摘要，不扩大摘要覆盖。
